# ui/src/contract_types

Generated TypeScript types and parsers for the contracts the UI reads (REQ-UI-001, REQ-API-001, AGENT-15). **Nothing here is edited by hand**: `python3 -I tools/codegen/generate.py --write` regenerates it from `contracts/schemas`, and `--check` (run by CI) fails when a file differs or was added by hand.

- Which contracts: `tools/codegen/ts.json` (the roots the UI reads); the contracts they refer to are generated with them.
- `parseX(value: unknown): X` for every type: it refuses what the schema refuses at the shape and at the bounds a parser can hold (JSON types, required and unknown members, enums, constants, whole-string patterns, string lengths in code points, number bounds, list lengths, `oneOf`) and at the conditional rules of the schema (`prefixItems`, `allOf`, `if`/`then`/`else`, `not`, `anyOf`, `contains`; written as checks, see `tools/codegen/README.md`). A `ContractError` names the place and the rule, never the value.
- The UI parses every response and every SSE event before it shows anything, so it shows only what a contract admits and never anything outside it (PERD §40.4).
- Tests: `ui/test/contracts.test.mjs` runs every valid and invalid fixture of the customer and operator contracts through the parsers: every valid one parses and every invalid one is refused (noema#682), `ui/test/benchmark_contracts.test.mjs` does the same for `scorecard-view.v1`, and `ui/test/approver_contracts.test.mjs` for `confirmation-answer.v1`. Run: `cd ui && npm test`.
- Entry points (A258): import from `customer.ts` in a customer-facing page (the four public contracts and `errors.v3`) and from `operator.ts` only in the operator and auditor UI (adds `reconstruction.v3` and `record-event.v3`, which carry `tenant_id`, the full events and their hashes). `benchmark.ts` is the third, for the benchmark UI (`ui/bench`, REQ-UI-004) only: it parses `scorecard-view.v1` (the approved aggregate view of a run, A250: counts and rates, no case id, no failure list, no oracle or held-out reference, INV-22) and imports nothing but the runtime and that view; no customer or operator entry point reaches it, and it reaches none of theirs (`tools/codegen/test_codegen.py`, `ui/test/benchmark_contracts.test.mjs`). There is no `index.ts`.
- The fourth entry point, `approver.ts` (noema#760, after #758): it parses `confirmation-answer.v1`, the closed `{request_id, response}` body an approver sends (identity is never in the body, INV-12; ACCEPT leads to a fresh Trust evaluation, not a grant, INV-25). It imports the runtime, that one module and the two shared definition files it refers to (`common_v1`, `enums_v1`); no customer, operator or benchmark entry point reaches it, so the customer bundle holds it only if a page imports `approver.ts` (`ui/test/approver_contracts.test.mjs` fails for any page not named in its allowlist). Which pages and roles may import it is not decided here.
