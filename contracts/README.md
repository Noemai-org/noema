# contracts

Canonical, versioned contracts (JSON Schema 2020-12, `<name>.v<major>.json`). Owner series: CON-01.

- `schemas/`: the schemas (CON-01: C-1 to C-6, the candidates read contract and the reconstruction response contract).
- `fixtures/valid/` and `fixtures/invalid/`: one of each per schema.
- `fixtures/golden_vectors.json`: existing evidence-set hash vectors; see `fixtures/README.md`.
- `fixtures/digit_run_vectors.json`: the shared vectors of the digit-run rule for the Record guard, the model service's redactor and the UI scan (a fixture, not a contract); see `fixtures/README.md`.
- `fixtures/candidate_ranking_vectors.json`: the shared vectors of the candidate ranker (REQ-AMB-003, A555, A559, A560), integer basis points; loaded by the Go ranker (`services/core/platform/candidaterank`) and the Python reference (a fixture, not a contract); see `fixtures/README.md`.

Changes need both founders (CODEOWNERS). A contract change follows AGENT-15: version bump, migration note, regenerated models.

**Vendored copies of docs files.** These files are copies of originals in `Noemai-org/docs`; the original wins on any difference. Each starts with a comment naming the docs commit it was taken from: `AGENTS.md`, `CLAUDE.md`, `contracts/state-registry.md` and `contracts/perd-32-2-event-types.md` (an extract of PERD section 32.2). One command re-points all of them to a clean docs checkout: `python3 tools/vendor/repoint_docs.py --docs <docs checkout>` (add `--check` to only report differences). The current PERD file for the extract is read from the docs checkout's `docs/poc/perd/README.md` (the row marked "Current."), so a PERD version bump needs no change to the script.

## Record event v3 (27 Oct 2026)

`schemas/record-event.v3.json` and `schemas/reconstruction.v3.json` sit beside v1 and v2, which are not edited (AGENT-15; a test pins their bytes). Decision record: `DEC-2026-10-27-actor-and-payload-hash` in `Noemai-org/docs`; the text they follow is PERD v1.17 §32.1.

- **What v3 is.** v2 with the emitter, the principal and `payload_hash` defined. `schema_version` is major 3. `written_by` is one of 17 service identities (the ten of the PERD §41.1 table and the seven §34.1 logical services whose adapters carry an identity; `fault-controller` and `fixture-loader` are benchmark-only and not emitters). The machine-readable table is `services/core/record/chain/actors.json`; the core derives its sets from it and accepts 16 of the 17 (the benchmark runner's identity is in the contract and refused by the core). `actor` is required and is `<kind>:<id>` (kind: customer, operator, approver, auditor, regulator, admin; id the session token's `sub`, no colon) or, when no authenticated person caused the event, the emitter's own identity, equal to `written_by` (a rule per emitter in the schema). `service` is not a principal kind. `payload_hash` is SHA-256 of the UTF-8 RFC 8785 form of the payload, integers only; an event that refers to no object has the payload `{}`. The event types, security kinds, nine grant-void reasons and failover reasons are those of v2.
- **Migration note.** `actor` changes meaning and form, so v3 is not additive (new major, v2 unchanged). No v2 event exists outside tests and fixtures, so nothing is migrated: the writer (`services/core/record/chain`), the verifier, the ledger (emitter `core-execution`) and the benchmark runner's reader (`reconstruction.v3`) move together. No generated models exist yet (CON-03).
- **Generated files.** `python3 -I tools/record_chain_ref_v3.py --write` writes the v3 fixtures and the `record_event_chain_vectors_v3` family; `--check` (also run by `tools/contracts/test_record_event_v3.py`) fails on any difference. v2 is still written by `tools/record_chain_ref.py`, and its output did not change. The `payload_hash_vectors` family comes from `tools/payload_hash_independent.js` (Node), not from the generator.
- **Tooling.** `tools/jcs_ref.py` is the Python RFC 8785 for the generators: it sorts members by UTF-16 code unit and refuses any number that is not an integer within 2^53-1.

## Intent Object v2 (12 Nov 2026)

`schemas/intent-object.v2.json` sits beside `intent-object.v1.json`, which is not edited (AGENT-15; `tools/contracts/test_intent_object_v2.py` pins its bytes). Ruling A163 of the Architect (12 Nov 2026; the question is noema#475, asked by C1). Task A163.

- **What v2 is.** v1 with `schema_version` major 2 and one relaxed pattern: `principal.asserted_by` is `^[a-z][a-z0-9_-]*$`, so it may contain `-`. The session's verified issuer is `noema-poc-idp` (ruling A1, exact match), which v1's `^[a-z][a-z0-9_]*$` refused. The new pattern is as strict as the old one everywhere else: it starts with a lower-case letter and allows no dot, slash, colon, space, upper-case letter or non-ASCII character (a test lists the edges). A test fails if v2 differs from v1 anywhere but `$id`, the top description, `schema_version` and that pattern.
- **Not changed.** `principal_id` (`usr_…`), `principal_type` and `authn_ref`. Whether the edge refuses a `sub` that is not `usr_…`, or the contract is relaxed, is still open on noema#475.
- **Migration note.** Relaxing a pattern is not breaking for a reader of v2, but a v1 reader refuses a v2 object that uses `-`, and the major in `schema_version` says which one a document is. A document is v1 or v2, never both (tests). No Intent Object exists outside tests and fixtures, so nothing is migrated. The model service still compiles v1 (it has no compile route yet); the core gate (noema#453) decodes `IntentObjectV1` and does not enforce patterns, so it accepts a v2 object's identity block unchanged. Moving the gate to `IntentObjectV2` is a follow-up that lands with the Go-side pattern validation (A158), after both PRs are on `main`.
- **Fixtures and models.** `fixtures/{valid,invalid}/intent-object.v2` are every v1 fixture with `schema_version` 2.0, plus a valid hyphenated issuer and invalid `asserted_by` cases (upper case, leading hyphen, leading digit, dot, slash, space, empty, trailing newline) and a major-1 object. Generated Go and Pydantic models come from `make codegen`; `tools/codegen/shape_refusals.json` is regenerated by `tools/codegen/shape_refusals.py --write`.

## Intent Object v3 and Intent Slot v2 (13 Nov 2026)

`schemas/intent-slot.v2.json` and `schemas/intent-object.v3.json` sit beside `intent-slot.v1.json`, `intent-object.v1.json` and `intent-object.v2.json`, none of which is edited (AGENT-15; `tools/contracts/test_intent_object_v3.py` pins their bytes, and `common.v1.json`'s). Ruling A166 (2) of the Architect (recorded in docs#159) and A173. Task CON-01 (the contracts). PR noema#520.

- **What it is.** Every confidence is an integer number of basis points, a new def `BasisPoints` (integer, 0 to 10000; 1 = 0.01 percent) in `intent-slot.v2`. `intent-slot.v2` is v1 with the `confidence` of its five slot shapes as `BasisPoints`; `intent-object.v3` is `intent-object.v2` with `schema_version` major 3, `slots` from `intent-slot.v2` and `source.asr_confidence` as `BasisPoints` (null stays legal: a text turn has none). `asserted_by` is as in v2 (it allows `-`). `common.v1` and its fractional `Ratio` are not edited, and `canonical-input.v2` keeps `Ratio` (it is handed to the model and never hashed or signed).
- **Why.** `crypto.CanonicalJSON` refuses a fractional number before it canonicalises, so no hash or signature can be computed over an object that holds `0.93`. A166 (2): the fix is in the data, not in the canonical rule. A test shows both halves (a v2 object with a confidence cannot be canonicalised; every valid v3 fixture can).
- **Who converts.** The producer, at its boundary: the model's proposal asks for integer basis points, and the schema gate refuses a fractional number as a shape error (it never rounds model output). The ASR adapter converts the engine's ratio to basis points at its boundary. Neither adapter exists yet; nothing converts in this PR.
- **Migration note.** A new major (the type of a field changes), hence v3; v1 and v2 stay valid for what they describe. A document is v2 or v3, never both: a v3 object does not validate as v2 (its confidences are over 1) and a v2 object does not validate as v3 (its version and its ratios). No Intent Object exists outside tests and fixtures, so nothing is migrated. The model service and the core gate still decode v1 (the gate moves to `IntentObjectV3` with the A158 Go-side validation, a follow-up).
- **Fixtures and models.** `fixtures/{valid,invalid}/intent-object.v3` are every v2 fixture with the scale and the version changed, plus the edges (0 and 10000, a null ASR confidence; fractional, over range, negative, string, boolean, in a slot and in the source, and a major-2 object). `fixtures/{valid,invalid}/intent-slot.v2` do the same for the slot and the `BasisPoints` def. Generated Go and Pydantic models come from `make codegen`; `tools/codegen/shape_refusals.json` is regenerated by `tools/codegen/shape_refusals.py --write`.

## Decision Record v2 (6 Nov 2026)

`schemas/decision-record.v2.json` sits beside `decision-record.v1.json`, which is not edited (AGENT-15; `tools/contracts/test_decision_record_v2.py` pins its bytes). Rulings A5 and A13 of 6 Nov 2026 (record: docs#117, still Proposed, so noema#168 says "do not merge before docs#117"). Task TRU-05.

- **What v2 is.** v1 with `schema_version` major 2, two new required fields, `issued_at` and `expires_at` (simulated clock), and a defined `sig` (A13): HMAC-SHA-256 with the grant keys over the domain label `noema/decision-record/v2`, one `0x00` byte, and the RFC 8785 (JCS) form of the record without `sig.value`. `sig.key_id` stays in the signed bytes, so a signature cannot be re-attributed to another key. The bound fields are `intent_id`, `correlation_id`, `policy_version` (`policy_id@version`), `issued_at`, `expires_at` and `key_id`; a record missing any is invalid. v1 already carried `intent_id`, `correlation_id` and `policy_version`; A5's "adds" is read as "requires in v2".
- **Migration note.** v1 records have no defined signature rule and no `issued_at`/`expires_at`, so v2 is a new major and v1 is not edited. A v1 record does not validate as v2 (tests). The reverse is not true: v1's version pattern is generic, so a v2 record also passes v1's pattern; readers dispatch on `schema_version`. No v1 record exists outside fixtures; the Decision Record writer (TRU-05 Go side, not built) writes v2 only. No migration tooling: this is the synthetic POC.
- **Fixtures and models.** `fixtures/{valid,invalid}/decision-record.v2` are the v1 fixtures with version 2.0 and the two new fields, plus invalid records that miss each bound field or carry major 1. Generated Go and Pydantic models come from `make codegen`.

## customer-answer.v1, overlay-card.v1, errors.v3 and reconstruction.v3, three tightenings of the digit-run pattern (A308, A317 to A328, interim)

- **What changed.** A minor change in place (AGENT-15; the files keep their names). The one definition of the pattern is `tools/contracts/digit_run.py`; it is written into 17 members (`customer-answer.v1` 8, `overlay-card.v1` 5, `errors.v3` 3, `reconstruction.v3` 1) and, for the facts of `reconstruction.v3`, into the two `FACT_VALUE` members. (1) U+001C to U+001F join digits, as they already do in the Record guard's separator class (A308). (2) A second rule: **ten or more digits joined by separators or by ASCII commas are refused.** Exactly: a run is a stretch that starts and ends with a digit of any script (Nd) and has between its digits only characters of the core's separator set or ASCII commas (U+002C); the string is refused when a run holds ten digits or more. A comma still ends a run of the first rule (five digits joined by separators), so `12,345`, `20,000,000` and `NGN 123,456,789` pass, and `1,234,567,890`, `4111,1111,1111,1111`, `4111, 1111, 1111, 1111` and `5,000, 3,000, 2,000` do not. The ruling's money clause (a whole money string of at most nine integer digits is exempt) is not written into the pattern because it changes nothing here: a money string with ten digits or more holds `ddd.dd` (five digits joined by the point), which the first rule refuses already. (3) The minted-ID branch of a fact value is exactly `<prefix>_<ULID>`: a lower-case prefix of two to six letters and a ULID of 26 characters, the first `0` to `7`, the rest Crockford base 32 (upper case, no I, L, O, U), with a letter in it. Every other typed ID (`recev_1005`, `usr_8821`) is no exemption and meets the five-digit rule as any string does. The resource-reference branch is not changed (open question, `status/CON-digit-tightenings.md`).
- **Migration note.** All three are narrowings: nothing that was refused is accepted now, and nothing stored is rejected (these are outward and operator schemas; the Record is not validated against them). A document stops validating if a free-text member holds digits joined by U+001C to U+001F, ten digits or more joined by commas (outside a string the first rule accepts), or a fact value of the form `<prefix>_<body>` that is not a ULID and holds five digits in a row (`ab_` and 30 digits and `a`; `ten_4111111111111111a`). No committed valid fixture holds one: none was edited. A producer that renders a list of numbers with commas (`5,000, 3,000, 2,000`) into a free-text member now has to break the list or round it; this is the price of the ruling's wording, stated for the Architect. `benchmark-case.v1` is untouched. Regenerated: the Pydantic and TypeScript models (the Go models do not carry the pattern). No consumer of the Record guard, the redactor or the UI scan changes here: they belong to noema#709, and this schema is their second layer.
- **Tests.** `tools/contracts/test_public_api.py` (`DigitRunTightenings`, the minted-ID test, the fact-value lists; an oracle written from the definitions gives the verdict on 6000 random strings), 14 invalid and 3 valid fixtures (customer-answer, errors.v3, overlay-card, reconstruction.v3; the reconstruction ones are generated by `tools/record_chain_ref_v3.py`), and the TypeScript parsers in `ui/test/contracts.test.mjs`.

## message-request.v1, a new contract: the body of a customer's message (PERD 39.2, ruling A275)

## pack.v1 gains `handoff_routes` (A531, interim, relayed, not yet committed; PCK-07)

- **What changed.** `pack.v1` gains an optional `handoff_routes`: a non-empty list of `{reason_code, owner_queue, intent_nodes?}`. `reason_code` is a `CoreReasonCode` (the `enums.v1` enum, `$ref`), `owner_queue` is a queue id, and `intent_nodes` is an optional non-empty, unique list of node ids; absent means every node. It is the data behind `Handoffs.Routed` (noema#896): Trust asks whether the pack routes a reason to a handoff; the orchestrator raises the alert on the reason. Additive and optional, so the file keeps its name (the rule of the `case_reasons` entry above); no new version file. Regenerated: the Go and Pydantic models and `tools/codegen/shape_refusals.json`.
- **Migration note (AGENT-15).** Nothing that validated before stops validating: a pack without `handoff_routes` routes no handoff, which is what the intake already does when the port answers "not routed". A consumer with its own copy of the pack shape gains one optional member. The fintech pack declares one route, `NO_RUNNABLE_CAPABILITY` to `PAYMENTS_OPERATIONS` for every node, and its manifest pin is updated in the same change.
- **Checks (not in the schema).** `packcheck`, check `routing`: the queue is in `routing_allowlist` (a free-form destination is not representable, REQ-AG-002), a reason code is routed at most once (that it is a core code is the schema's), and every named intent node is declared by the pack.
- **Tests.** Fixtures `valid/pack/with_handoff_routes.json` and six `invalid/pack/handoff_route*.json`; `tools/packcheck/test_packcheck.py::HandoffRoutes`.

## decision-record.v2: the basis members are required keys, null for an early outcome (A574 and A577, interim; TRU-05)

- **What changed.** `evidence_snapshot_id`, `policy_version` and `evidence_freshness` stay in `required` and now accept `null`. One conditional rule: for an ALLOW or a CONFIRM none of the three is null. A null is the truthful value for an outcome reached before the evidence and the policy were evaluated (REJECT, CLARIFY, WAIT, ESCALATE, UNKNOWN); no outcome may omit a key, and no marker is added (A577). The decision-basis text this follows is `trust/decide/basis.go` (REQ-TRU-001, DEC-2026-10-18): an early refusal needs only the pack version and the time.
- **Migration note (AGENT-15).** `decision-record.v2` changes in place, with no new major, because no consumer reads an early record yet (the Writer still records a decision with a complete basis, A578). Every record valid before is still valid: the three members were already present and non-null in every one. A consumer must now accept null in these three members for an outcome other than ALLOW or CONFIRM: the generated Go fields are `*CommonV1SnapshotId`, `*string` and `*[]DecisionRecordV2EvidenceFreshnessItem`, and the Pydantic fields allow `None`. `decision-record.v1` is unchanged. Migration 0038 makes the table agree (see `services/core/migrations/README.md`). Changes under `/contracts` need both Founders (CODEOWNERS).
- **Tests.** Fixtures `valid/decision-record.v2/{reject,escalate,unknown}_early_null_basis.json` and `invalid/decision-record.v2/{allow_null_evidence_snapshot_id,allow_null_evidence_freshness,confirm_null_policy_version,reject_without_evidence_snapshot_id}.json`; `tools/contracts/test_decision_record_v2_basis.py`; `services/core/platform/db/decision_basis_nullable_test.go`; `services/core/trust/grants/record_null_basis_test.go`.

## intent-node.v1 `disambiguation` gains `options_key`, `display_template` and `attribute_order` (ruling A555, interim, relayed, not yet committed; REQ-AMB-004, REQ-AMB-003)

- **What changed.** The intent node's `disambiguation` block gains three optional members: `options_key` (the pack's question key for OPTIONS mode, a pack template id like `clarification.v1` `question_key`), `display_template` (the label of one candidate in OPTIONS mode) and `attribute_order` (the pack's fixed order of askable attributes, 1 to 8 items `{name, question_key, label_template}`; ask by attribute, DEC-2026-10-20 D4). They fill `intake.Disambiguation.OptionsKey` and `AttributeOrder` (`decide.AttributeSpec`), which the Go intake already had and the pack could not feed. Additive and optional, so the file stays `intent-node.v1.json` (the rule of the `write_when` and `handoff_routes` entries above); no new version file. Regenerated: the Go and Pydantic models (`tools/codegen`; `shape_refusals.json` is unchanged).
- **Checks (not in the schema).** `packcheck`, check `disambiguation`: the three go together or none, and only on a node with a `candidate_search` slot; attribute names are the candidates contract's labelable fields (every `candidates-response.v1` Candidate field except `candidate_id`, `resource_ref` and `beneficiary_alias_match`, and not `currency`, which is shown with the amount), each once; question keys are listed once and `options_key` is none of them; a template is literal text and `{attr:<field>}` placeholders only: at least one placeholder, each a labelable field (an attribute's label shows only that attribute, the amount also its currency), no two side by side, no brace that is not a whole placeholder, and no digit in the literal text, in any script. So a label can show at most the digits of the masked values (the four of `account_last4`), and the Labeller formats the amount.
- **Migration note.** Nothing that validated before stops validating. The fintech pack declares the three members on the investigate node (the only node that searches candidates); its manifest hash is re-pinned. The attribute order (time, recipient, account, amount) and the template wording are SYNTHETIC pack data, not stated by the PERD, and are the Founders' to review as data (A538's rule); the question WORDING for each `question_key` is not here (the pack's explanation templates are keyed by outcome and classification), so a Labeller or UI needs it before a question is shown.
- **Tests.** `tools/contracts/test_intent_node_candidate_labels.py`, `tools/packcheck/test_packcheck.py` (class `CandidateLabels`), `contracts/fixtures/{valid,invalid}/intent-node`.

## capability-descriptor.v2, `tenant_zone` and the intent node's `action_graph` (rulings A631, A645, A647 and A650, interim; REQ-CAP-004, REQ-DATA-002; AGENT-15)

- **What changed.** `capability-descriptor.v2.json` is a new file and v1 is untouched. `compensation` is the enum `NONE_REQUIRED`, `INVERSE_CAPABILITY`, `ESCALATE_ONLY`; `inverse_mapping` `{capability_id, parameters}` is required with `INVERSE_CAPABILITY` and refused with any other value; every other member is v1's. `pack.v1` gains the optional `tenant_zone` (an IANA name) and its `capabilities` items now reference descriptor v2. `intent-node.v1` gains the optional `action_graph` (a pack id): the graph whose write capability an admitted intent of the node confirms.
- **Migration note.** `pack.v1` is changed in place, with no `pack.v2`: the `$ref` change makes a pack whose capabilities carry a v1 `compensation` string invalid, and every pack in the repository is migrated in the same PR (the fintech pack and the three conformance packs; the pack fixtures of `contracts/fixtures`). The mapping is: a prohibited capability declares **no** compensation (A647, BD-08); an IRREVERSIBLE allowed capability declares `ESCALATE_ONLY` (`log_complaint_reference`, `record_investigation_evidence`); any other allowed capability declares `NONE_REQUIRED` (what `none_required` and `not_applicable` meant). The pack manifest's own schema is unchanged, so it takes no new version: the fintech manifest re-pins the hash of `fintech_v1.json`. `tenant_zone` and `action_graph` are optional, so a pack without them still validates. `capability-descriptor.v1.json` stays for history; no pack references it.
- **Checks (not in the schema).** `packcheck`, checks `compensation`, `tenant_zone` and `graph_link`: a REVERSIBLE or COMPENSABLE capability declares a compensation; an IRREVERSIBLE one declares `ESCALATE_ONLY` and nothing else; an inverse capability is registered, not prohibited and not itself; a prohibited capability declares none; a zone is one the tz database knows; a node's graph is one the pack declares. The Go registry (`execution/registry`) refuses an allowed capability with no compensation and a prohibited one that declares one.
- **Recon-rule window (A659, interim, relayed, not yet committed; amends A641 and A647).** `recon-rule-set.v1.json` is a new file: the shape of the pack's rules file, member for member as `trust/reconcile` reads it. The declared window of a compared pair is `convergence_window_seconds` (not A647's `window_seconds`), on each `incompatible` pair and each `single_valued` field; from rule-set version 2 it is required (a whole number of seconds, at least 1) and in version 1 it is not allowed. The fintech rules file stays version 1 with no window, so it validates unchanged and the loader on `main` reads it as before; moving it to version 2 with its windows is PCK-05's data change (EL), which also moves the evidence mapping's `ruleset` and `expected.recon_rule_set_id` to `fin.recon.rules@2`. The loader of #949 reads the member; its parser refuses an unknown member, so no version 2 file loads until that PR is on `main`. Packcheck checks the listed rules file against this schema (manifest check) but does not yet check that a window equals the smaller freshness limit of its pair (A641): that needs the entity-to-source link of the evidence mapping, and is OD-P-107's open part.
- **Write capability and `write_when` (SR's request on noema#935; no contract change).** `packcheck`, check `write_when`: an intent node whose `action_graph` calls an allowed capability of a risk class above R0 carries a `write_when`, because the Writes rule reads a node with none as never writing. The fintech pack already complies; no pack data changes.
- **Tests.** `tools/contracts/test_capability_descriptor_v2.py`, `tools/packcheck/test_packcheck.py` (classes `Compensation`, `TenantZoneAndGraphLink`), fixtures `{valid,invalid}/capability-descriptor.v2`, `execution/registry` tests; for A659 and the `write_when` link: `tools/contracts/test_recon_rule_set.py`, `tools/packcheck/test_packcheck.py` (classes `ReconRuleSet`, `WriteWhenLink`), `tools/packcheck/test_manifest.py` (class `ReconRulesFile`), fixtures `{valid,invalid}/recon-rule-set`.

## execution-receipt.v1, `step_params` added in place (A692, interim, relayed; OD-P-119; REQ-EXE-006, REQ-AUD-006; AGENT-15)

- **What changed.** `execution-receipt.v1.json` gains an optional `step_params`: an object, never empty (`minProperties` 1), whose keys are slot names (`common.v1#/$defs/SlotName`, the keys of a plan step's `params`) and whose values are what a plan step param may hold (string, integer, boolean or null). It carries the params of the executed plan step that the outcome definition's `PLAN_PARAM` bindings name, and only those, so the Outcome request builder reads a `PLAN_PARAM` variable from the signed receipt. It is absent when the definition has no `PLAN_PARAM` binding. Additive and optional, so the file keeps its name (A698: additive optional members stay in the current version until the `contracts-v1.0.0` tag; no new version file). Regenerated: the Go and Pydantic models and `tools/codegen/shape_refusals.json`.
- **Migration note.** Nothing that validated before stops validating: a receipt without the member is unchanged and still verifies, because the signature is over the whole canonical document (`outcome/receiptsig` tests it with and without the member, and after removing, changing or adding it). No Execution code fills the member yet; that is a follow-up PR in Execution, which keeps it to the bound params (AGENT-13). No stored receipt, migration or reader changes meaning.
- **Check (not in the schema).** That only the bound params appear needs the pack's outcome definition, which the schema cannot see; the Controller's follow-up PR holds it with a test.
- **Tests.** `tools/contracts/test_receipt_step_params.py`, `internal/contracts/receipt_step_params_test.go`, `outcome/receiptsig/step_params_test.go`, fixtures `{valid,invalid}/execution-receipt`.
