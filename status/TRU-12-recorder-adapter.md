### Pre-work: CONFIRMATION_EXPIRED in the superseding CONFIRM's transaction (NOT implemented; for a later lane after noema#755 and noema#756 merge)
What the later lane needs, read from noema#755 (`feat/TRU-12-intake-declined` at 7e02f918) and noema#756 (`feat/TRU-12-confirmation-store` at 24bd1a75):
1. From #755: `intake.Recorder` gains `RequestConfirmation(ctx, intake.ConfirmationRequest) (string, error)` (TenantID, CorrelationID, RequesterID, IntentID, IntentVersion >= 1, IntentHash, Requirement, TTL, Binding FreshBinding). Status is pure; the Recorder persists the request with its CONFIRMATION_REQUESTED event, so the Record comes first (PERD 32.4). `RecorderAdapter` therefore needs a new method, in a new file (`recorder_confirm.go`), not a change to `Record`.
2. From #756: the store is `trustpg2.Requests{Pool, IDs, Events}` with `Open(ctx, NewRequest) (string, error)` (NewRequest carries `Supersedes`, TTL counted by the DATABASE clock, Version >= 1), `Expire(ctx, tenant, requestID) error` (records CONFIRMATION_EXPIRED once, via the `confirmation_expiry` table, only when the request has expired on the database clock: `ErrNotExpired` otherwise) and `Answer`. The Record events go through `trustpg2.RequestEvents{Requested, Received, Expired}` which the store calls BEFORE it commits.
3. The gap this adapter must close: `Requests.Open` and `Requests.Expire` each own their transaction today (the store calls `Events` then commits). The superseding CONFIRM must write CONFIRMATION_EXPIRED for the superseded request AND CONFIRMATION_REQUESTED for the new one in ONE transaction (A363/(4): "written by the Recorder in the superseding CONFIRM's transaction"). So the later lane needs from #756 either (a) `Open`/`Expire` variants that take a `pgx.Tx` the caller owns (the shape `recorder.Writer.Write(ctx, tx, ...)` already has), or (b) the Recorder adapter to own the transaction and the store to expose `OpenTx(ctx, tx, NewRequest)` and `ExpireTx(ctx, tx, tenant, id)`, with `RequestEvents` implemented by an adapter that appends through `chain.Appender` on the same `tx` (the adapter already holds `Appender`). Recommended: (b), same pattern as `Record`: one `TxBeginner`, one commit, rollback on any error, the same `TxTimeout`/`commitBound` handling, `ErrNoDeadline` first.
4. Ordering inside the transaction: `ExpireTx(previous)` first (it refuses with `ErrNotExpired` if the database clock says the request has not expired: then the new request is a supersession of an ANSWERED request, and no EXPIRED event is written; the trigger in 0032 already allows supersession only after an answer or an expiry), then `OpenTx(new, Supersedes: previous)`. Both events are appended on the same `tx`; if the append fails, nothing is stored (EC-E16).
5. What the Recorder needs to know to choose: whether the previous request was answered or only expired. That is a read of `Latest(ctx, tenant, principal, intent, version)` (`RequestRecord.Answer`): answered means no EXPIRED event; unanswered and past expiry means EXPIRED then the new request. The decision is the store's database-clock comparison, never the adapter's clock (A368 (ii)).
6. Tests for that lane (red first): both events appear together or neither; a failed append rolls back the supersession; `ErrNotExpired` on an unexpired unanswered request means the new request is refused (one open request per action); an answered predecessor writes no EXPIRED; a retry after a failed commit does not write EXPIRED twice (the `confirmation_expiry` mark).
7. Do not touch: `trust/confirm`, migration 0032, `port.go`, `dispatches.go`.
