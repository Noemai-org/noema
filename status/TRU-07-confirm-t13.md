## Flagged for the Architect and EL (read these first)

1. **CONFLICT DETECTED, stop condition: Declined -> REJECT at T13 (SoT 43.2a step 4, PERD REQ-TRU-009, PERD 23.3).** The order says Declined becomes REJECT `DECLINED_BY_APPROVER`. PERD 23.3 gives T13 the terminal result **CONFIRM** only ("T13 | Confirmation requirement (profile approvals) | CONFIRM"), and `trust/decide` enforces it: `stepOutcomes[T13Confirmation] = {Confirm}` (`evaluate.go`; pinned by `evaluate_test.go`). A REJECT returned from T13 is refused by `accepts` as an invalid result and becomes UNKNOWN INTERNAL_ERROR, after the REJECT had been recorded. The same PERD table lists `DECLINED_BY_APPROVER` as produced by "Confirmation DECLINE (SoT 43.2a)", so the PERD contradicts itself between the step table and the reason table; SoT 43.2a (higher authority) says the decision closes as REJECT. The change needed is Tier 1 and is not mine to make: (a) a PERD/plan ruling that T13 may end in REJECT (a new PERD version file plus a decision record), (b) `stepOutcomes[T13Confirmation] = {Confirm, Reject}` and its pinned test in `trust/decide`, (c) the intake mapping, which is small: in `t13`, `case ConfirmationDeclined:` requires `RequestID` well formed and no `NewRequest`/`EventID`, builds `r.Reject(passed(), decide.Core("DECLINED_BY_APPROVER"))` with `e.withBasis`, calls `Recorder.Record` once with no steps and no request, requires a decision ID and no grants, and returns `decide.Stop(d)`; the Writer already stores such a decision (tested here). Until then Declined is UNKNOWN INTERNAL_ERROR, nothing planned, nothing recorded (`TestT13DeclinedIsUnknownForNowAndNothingIsPlannedOrRecorded`, whose comment now says why; it replaces nothing because the REJECT is not built).
2. **A186 collision (design item F): one decision per input tuple, enforced by the database.** `decision_record_input_key` (migration 0027) is a UNIQUE index over (tenant, intent id, intent hash, evidence snapshot, policy version). Today's lookup returns the stored decision only when the outcome agrees and otherwise `ErrDecisionConflict`; it never returns "the stored CONFIRM" for a different outcome. So after a stored CONFIRM, an ALLOW (after a given confirmation) or a REJECT DECLINED_BY_APPROVER on the **same tuple** is `ErrDecisionConflict` and writes nothing, and no Writer-only change can record it: the index would refuse the second row. Making it record needs a forward-only migration changing the index (for example adding the outcome) and a ruling on INV-21 (the tuple does not contain the confirmation state, so "same input, same decision" already does not cover T13). This is the A186 single-decision rule (Tier 1), so I stopped and changed nothing in lookup. The behaviour is pinned (interim, fail closed): `TestAStoredConfirmAnswersItsTupleOnlyAndAnotherOutcomeOnTheSameTupleIsAConflict` shows the conflict on the same tuple and a new decision on a new snapshot. **Consequence for EL:** a re-evaluation after an ACCEPT or a DECLINE must read a **new sealed snapshot** (A186; open point 1 on noema#527), else its ALLOW (or REJECT) cannot be recorded and the evaluation ends in UNKNOWN. Please confirm the Evidence adapter seals a new snapshot per evaluation; if it reuses the snapshot id the confirmed ALLOW can never be written.
3. **T11 CONFIRM is not recorded and creates no request.** When the policy rule's effect is CONFIRM, T11 stops with CONFIRM and never reaches T13 (unchanged by this PR). Such a CONFIRM has no Decision Record and no request, so an approver has nothing to answer. The order covers T13 only; T11's CONFIRM needs the same recording (and a `Confirmations`-independent source of the requirement and TTL). Not built, not decided here.
4. **Interim design defaults A to G** (below) are mine, from the relayed order, and are listed with how each was resolved. A few depart from or add to the order and are marked **(added)**.
5. **Payload guard (A184).** Checked, not weakened. The contract's example target `fin.transaction:TX88213` (a run of five digits) is accepted at `/target_ref` (ruling A193, DEBT-30). Any other member with a run over four digits is refused and fails the whole write: a requester or principal that is a bare number (`usr_88213`, body of digits only) is refused. Real IDs are ULIDs and pass. Tested.
6. **Reconstruction.** `record/reconstruct` projects CONFIRMATION_REQUESTED through an allow-list (`authorityKeys`): only `capability_id` and `policy_version` of the payload are served (plus the object_ref, the `cfr_` ID); the other members are not projected, so nothing breaks, and nothing of the request is shown to a reader. Changing that is out of this PR.
7. **`confirmation-request.v1` (the contract document)** has `display` and `sig`; the event does not carry them (no display text can hold a masked amount in the Record, and the signature is the confirmation store's). EL's adapter builds the contract document from the event plus the display it derives.

## What changed

### trust/intake (`gates_t13_t15.go`, `ports_t13_t15.go`, `intake.go`)
- `t13`: NotRequired continues (it must carry no `RequestID` and no `NewRequest`); Given continues (it must carry `EventID`, a well-formed `PlanHash`, a `cfr_` `RequestID`, and no `NewRequest`); Pending goes to `t13Confirm`; Declined and any other status, zero included, is UNKNOWN INTERNAL_ERROR (`errAnswer`).
- `t13Confirm` (Pending): exactly one of `RequestID` (open request) and `NewRequest` (make one); both or neither, or a `RequestID` that is not `cfr_...`, is UNKNOWN. Order: build the CONFIRM (`resolved`, `Confirm(passed())`, `withBasis`, digest) -> if `NewRequest`, `newRequest` -> `Recorder.Record` once -> check the answer -> `Stop(d)`. The CONFIRM is returned only if the Recorder wrote it: a Recorder error, no decision ID, a grant ID (no grant can follow a CONFIRM), a missing or malformed request ID for a request that was asked for, or a request ID for a request that was not asked for, each ends in UNKNOWN.
- `newRequest`: checks the spec (TTL at least one second, requirement in the contract enum), the two fresh values (evidence set hash in hash form, policy version in the binding's character set), the intent's own values (principal, intent hash), then `validPlan`; the plan must have exactly one step (else UNKNOWN `PLAN_INVALID`); capability and target must be in the binding's character set. It returns the request with `RequesterID` = the intent's principal (INV-12) and `ExpiresAt = e.now + TTL` (the evaluation's one clock reading, `Service.Clock`).
- `validPlan`: the Planner call, `wellFormed` and `planAgrees` of T14, moved into one function used by `t14` and `newRequest` (no behaviour change for T14; its tests pass unchanged).
- Types: `NewConfirmationRequest` (the eight values, `Requirement`, `RequesterID`, `ExpiresAt` in Unix seconds), `RecordRequest.ConfirmationRequest`, `RecordResult.ConfirmationRequestID`, `Result.ConfirmationRequestID`; `Result.DecisionID` is now also set for a CONFIRM that T13 recorded (still empty for any other).

### trust/recorder (`confirmrequest.go`, `recorder.go`, `doc.go`)
- `Request.ConfirmationRequest *NewConfirmationRequest`, `Result.ConfirmationRequestID`.
- `checkRequest` (inside `check`, before anything is written): only a CONFIRM may carry a request; the four hashes in the contract's form; `IntentHash` equal to the decision's; `PolicyVersion` equal to the policy the decision binds (`grants.BoundPolicy`); the requirement in the contract enum; a requester; `ExpiresAt` after `Writer.Clock.Now()`; the binding computable (`confirm.BindingHash`). Any failure is `ErrRequest`.
- On the new-decision path only: the `cfr_` ID is minted by `w.IDs.ID("cfr")` (form checked), the binding hash is computed by `confirm.BindingHash`, `DECISION_MADE` gets `confirmation_request_id`, and `CONFIRMATION_REQUESTED` is appended right after it, by `core-trust`, `object_ref` = the request ID, in the caller's transaction. The lookup path (stored decision) writes no event and returns no request ID.

## The exact payload of CONFIRMATION_REQUESTED

`written_by` `core-trust`; `actor` as DECISION_MADE's; `object_ref` the `cfr_` ID; same `correlation_id` as the decision; adjacent to its DECISION_MADE (`seq` + 1).

```json
{
  "confirmation_request_id": "cfr_...",
  "decision_id": "dec_...",
  "binding_hash": "sha256:...  (confirm.BindingHash of the eight values below)",
  "principal_id": "...", "intent_hash": "sha256:...", "capability_id": "...", "target_ref": "...",
  "params_hash": "sha256:...", "evidence_set_hash": "sha256:...", "plan_hash": "sha256:...", "policy_version": "policy_id@version",
  "approver_requirement": "SELF | MAKER_CHECKER | ROLE:<role>",
  "requester_id": "...",
  "expires_at": "2026-11-06T09:10:00.000Z"
}
```

`expires_at` is an RFC 3339 timestamp (SoT 43.2a writes it so; the Writer's request takes Unix seconds). The `DECISION_MADE` of a CONFIRM that created a request carries `confirmation_request_id` as well; one that named an open request, or any other decision, does not.

## What EL's adapters must now do
- **Recorder adapter** (`intake.Recorder.Record` with `recorder.Writer` in the one transaction it owns): map `intake.RecordRequest.ConfirmationRequest` to `recorder.Request.ConfirmationRequest` field for field (`ExpiresAt` stays Unix seconds); for a CONFIRM pass the `Decision` and `Evaluated` unchanged, **no steps, no `ConfirmationEventID`, no `ConfirmationPlanHash`**; return `RecordResult{DecisionID, ConfirmationRequestID: res.ConfirmationRequestID}` and **no grant IDs**. If the Writer returns the stored decision (retry of the same tuple) `ConfirmationRequestID` is empty and T13 then ends in UNKNOWN for a request it asked to create (fail closed; the next evaluation finds the request open through `Status`). Handle `ErrDecisionConflict` as an error (item 2 above). The CONFIRM and its request must be in the **same transaction** the adapter commits.
- **Confirmations adapter, `Status`:** read the open request from the Record (the CONFIRMATION_REQUESTED event of the tenant and the intent, not yet answered or expired): the event carries everything of the request, including the binding values, so Given can be recomputed with `confirm.BindingHash` from the six stored values plus the two fresh ones of `FreshBinding`. Pending **with `RequestID` and no `NewRequest`** when a request is open and unexpired (what to return for an open request whose binding no longer matches the fresh evaluation is a choice the order does not make: see the open questions); Pending **with `NewRequest` and no `RequestID`** when none is open (spec: requirement and TTL from the pack or configuration, never a number in Trust); Given with `RequestID`, `EventID`, `PlanHash`; Declined with `RequestID` (Trust treats it as UNKNOWN for now); NotRequired with none of them. Any other combination is UNKNOWN in Trust.
- **Approver route:** unchanged by this PR. It resolves a reply with `confirm.Resolve`, records it (`RecordConfirmation`) and triggers the fresh evaluation, which must seal a new snapshot (item 2).

## Design decisions A to G and how each was resolved
- **A. Who records what.** T13 calls the Recorder for Pending (CONFIRM) as ordered. For Declined it **does not** (stop condition, item 1); the authority layers for the CONFIRM are `passed()` as at T15, `r.Confirm(passed())` and `e.withBasis`, with `Record` carrying no steps. Resolved as ordered for Pending; blocked for Declined.
- **B. Request creation.** As ordered: Pending+RequestID records without a request (Planner not asked); Pending+NewRequest creates exactly one; both or neither is UNKNOWN; Given needs `RequestID` (as well as `EventID` and a plan hash); NotRequired carries none. **(added)** Given with a `NewRequest` is UNKNOWN; a malformed `RequestID` (not `cfr_...`) is UNKNOWN in every status that carries one; this tightens "Given path unchanged": a Given answer without a `RequestID` is now UNKNOWN (the PR 1 tests that built Given without one were given one).
- **C. Binding values.** As ordered: the plan comes from the Planner at T13 through the shared `validPlan`; exactly one write step; any other plan is UNKNOWN `PLAN_INVALID` (UNKNOWN is allowed at every step, so this is the result T14 gives); a Planner failure or a registry failure is UNKNOWN INTERNAL_ERROR, as in T14. A read plan (no step) cannot be bound: `PLAN_INVALID`. T14 still compares the plan hash with a Given confirmation's (A230), unchanged. **(added)** values outside the binding's character set (a space in a target, say) are UNKNOWN INTERNAL_ERROR rather than PLAN_INVALID: the intake keeps a copy of `confirm`'s character-set rule (`bindingValueRe`), because the intake may not import `trust/confirm` (doc.go); the Writer re-checks with the real one.
- **D. Expiry.** TTL from the spec plus the evaluation's one clock reading (`e.now`, from `Service.Clock`, SYNTHETIC in tests). I used `e.now`, not a second `Clock.Now()`, so the expiry is a function of the evaluation's inputs (INV-21). **(added)** A TTL under one second is refused (the expiry is whole Unix seconds); this is a unit guard, not a threshold. The requirement must match the contract enum (`SELF`, `MAKER_CHECKER`, `ROLE:[a-z][a-z0-9_]*`).
- **E. The Writer.** As ordered, with these choices: the request type is `recorder.NewConfirmationRequest`; the Writer mints the `cfr_` ID and the binding hash; the event is written right after DECISION_MADE in the same transaction and only on the new-decision path; `confirmation_request_id` is also in DECISION_MADE. **(added)** The Writer also requires the request's `IntentHash` to equal the decision's and its `PolicyVersion` to equal the policy the decision binds, because the later ALLOW recomputes the binding from those; where the intake's single-policy rule and `grants.BoundPolicy` disagree (two versions of one policy), the request is refused by the Writer (fail closed). `expires_at` in the payload is an RFC 3339 timestamp (SoT 43.2a), not Unix seconds, so that the payload guard needs no number. The caller's cfr id and hash cannot be supplied (no field). No guard was weakened.
- **F. A186.** Investigated: item 2. No Writer change made.
- **G. A repeated Record of the same CONFIRM tuple.** Writer level (real database): returns the stored decision, no second event (`TestARepeatedConfirm...`). Intake level: Pending+RequestID calls `Record` once per evaluation, with no request fields; two evaluations create one request in total (`TestT13ReEvaluationWhileARequestIsOpenCreatesNoSecondRequest`).
