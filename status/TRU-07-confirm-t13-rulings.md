## Flagged (read these first)

1. **Payload guard (A184) vs `ps:<hex>`: the guard was NOT changed, and CONFIRMATION_REQUESTED does not carry `policy_version` any more.** The payload guard (`record/payloadguard`) refuses a string with a run of more than four digits unless the whole string is a typed value (ID, `sha256:` hash, `hmac-sha256:` hash and so on). A 64-character hex holds such a run with a probability near one (the pinned composite of one policy, `ps:c1c966...`, holds `356053`), and `ps:` is not a typed value the guard knows. With the composite in the `policy_version` member the append of CONFIRMATION_REQUESTED fails, so no CONFIRM could ever be written (found when the Writer tests ran: "payloadguard: a payload string holds a run of more than four digits: /policy_version"). **Interim choice (mine, not a ruling):** the event carries the same hex as `policy_set_hash`, in the content-hash form `"sha256:<hex>"`, which the guard exempts; the reader rebuilds the composite as `"ps:" + hex`. The old `policy_version` member is gone from that event (DECISION_MADE and the Decision Record still carry the one policy they name). Pinned by `TestAConfirmationRequestBindsTheCompositeOf...` and `TestThePinnedCompositesHoldALongDigitRun...`. **Decision needed (Architect):** either keep this, or exempt `ps:` and 64 lower-case hex as one more typed shape in `payloadguard` (one line, next to `hmac-sha256:`; Record path, Tier 1, not mine to change) and put the composite back in a `policy_version` member (one line in `recorder.confirmationRequested`, plus the tests above). Either way the binding value, the intake and the ALLOW are unchanged.
2. **PERD 23.3 still says CONFIRM only for T13.** `trust/decide.stepOutcomes[T13Confirmation]` is now `{Confirm, Reject}` and its pinned test (`evaluate_test.go`, `permitted`) is changed with it, on the strength of the relayed ruling. **A PERD version file plus a decision record are still owed (docs repository, not this PR).** PERD's own reason table already lists `DECLINED_BY_APPROVER` ("Confirmation DECLINE (SoT 43.2a)"), so the step table and the reason table disagree today; SoT 43.2a step 4 says REJECT.

## The composite (the one formula)

`decide.CompositePolicyVersion(refs []PolicyVersionRef) (string, error)` in `trust/decide/policyset.go`, and `Basis.CompositePolicyVersion()` over the distinct (policy ID, version) of the basis rules. Same function for every caller.

1. For each ref build `policy_id + "@" + version`. A part that is empty or holds a character outside `A-Z a-z 0-9 _ . : -` (so also `@`) is `ErrPolicySetInvalid`. No ref at all is `ErrPolicySetInvalid`.
2. Remove duplicates; sort the strings as whole strings in byte order (`sort.Strings`; ASCII, so it is also UTF-16 code unit order). Note `a.b@1` sorts before `a@1` because `.` (0x2e) is below `@` (0x40).
3. Canonical form: the RFC 8785 form of the JSON array of those strings: `["a@1","b@2"]`, no white space, no escapes (the character set never needs one). This is checked against `platform/crypto.CanonicalJSON` in a Writer test, and against an independent Python implementation (`json.dumps(sorted(set(list)), separators=(",", ":"))`) for the golden vectors.
4. Composite = `"ps:" + lower-case hex of SHA-256(canonical form bytes)`: `ps:` and 64 hex characters, always, also for one policy version (no special case).

Vectors (SYNTHETIC): `["pol_synth01@3"]` -> `ps:50ca8c31e714463c1257e6e3f8b3f6c57fdb0c3fe471e8a2f015fa2b4f539ebb`; `["pol_synth01@3","pol_synth02@1"]` -> `ps:f81f4a1916c40274bfeb88b814e9b98bc36d43393b9cff1249f6b39c1fe364d1`; `["pol_synth01@2","pol_synth01@3"]` -> `ps:52a779a7fd72828f57e07726d30090c0beacc19b4b76fc1f06573b45d1d0c5d7`; `["fin.pol@3.1"]` -> `ps:c1c966ac3b0b555cd16913245fcdf40ebe103d30ea356053aca7a1be0b76967e`; `["fin.other@2.0","fin.pol@3.1"]` -> `ps:ec91c19602ebb2caf6db5ffb9113f0c26e54328be6d9c03c1c064485ac94a2cb`.

Where it is used: `intake.freshBinding` (the `FreshBinding.PolicyVersion` T13 passes and the `PolicyVersion` of a new request); `recorder.checkRequest` (the request's `PolicyVersion` must equal the composite of the decision's basis, else `ErrRequest`); `recorder.bindingOf` (the binding the ALLOW after a confirmation is spent against). All three use the one function. The value is inside `confirm.BindingHash`'s character set (`:` and hex), which `confirm` is untouched by.

## What EL's adapters must now do
- **Confirmations adapter, `Status`:** `FreshBinding.PolicyVersion` is the composite `ps:<hex>`; recompute a Given answer's binding with `confirm.BindingHash` from the six stored values plus the two fresh ones, **using the fresh `PolicyVersion` as passed**. Refuse (return an error for) a Given answer when either fresh value is empty (Trust refuses it as well). Read the request from CONFIRMATION_REQUESTED: the stored policy version of the binding is `"ps:" + hex(policy_set_hash)` (the member is `sha256:<hex>`; the member `policy_version` no longer exists on that event). A stored request whose policy set differs from the fresh one no longer matches: that is what makes an ACCEPT for another policy version never resolve (INV-25). Return `ConfirmationDeclined` with the declined request's `RequestID` and **no `EventID`** (and no `NewRequest`) for a decline; Trust records the REJECT.
- **Recorder adapter:** for a REJECT from a decline pass the `Decision` and `Evaluated` unchanged, **no steps, no confirmation fields, no `ConfirmationRequest`**; return `RecordResult{DecisionID}` only (no grant IDs, no request ID). `ErrDecisionConflict` is an error (flag 3).
- **Policies adapter:** keep `Versions` and `Rules` consistent (flag 5).
- **Evidence adapter:** unchanged: it must fill `SnapshotEvidence.EvidenceSetHash`, else no Given answer can ever stand (Trust now refuses it, not only the adapter).
