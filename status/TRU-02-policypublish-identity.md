### Decisions and what differs from the brief
1. **`session_user`, not `current_user`.** The brief said `current_user`. The code uses `session_user::text`: it is the login that authenticated, `SET ROLE` cannot change it, and every guard on this table (migration 0015) and `checkLogin` read the same thing. `current_user` would take the group role after a `SET ROLE trust_rw` (a mutant with it is killed by `TestASetRoleDoesNotChangeThePublisher`). The two are equal for a plain login.
2. **One statement.** `INSERT ... session_user::text ... RETURNING published_by`; the value that comes back is the event's actor. Go never reads the role first.
3. **Event shape: the role is the actor, not a payload member.** The actor `admin:<role>` is accepted by the chain (`personRe`: kind `admin`, id `[A-Za-z0-9][A-Za-z0-9_.-]{0,63}`; `trust_rw__ten_aa` fits). The payload keeps `policy_id`, `version`, `document_hash` and drops `published_by`, because the payload guard (A184) refuses a string with a run of more than four digits and `_` joins digits: every `internal/testpg` login is `trust_rw__<tenant>_t_<pid>_<n>` and a real tenant ID can hold digits. A mutant that put the role back into the payload fails the suite (the append is refused). The guard was not touched. Alternative if the Architect wants the role in the payload too: an exemption for a login-name shape in `payloadguard`, which is outside this allowlist. Another alternative: actor = `core-trust` (the emitter's own identity) with the role in the payload; it has the same guard problem and `admin` is documented as a person, so it was not taken.
4. **`--published-by` is simply not defined**, so it is refused as any unknown flag: exit 2, `policypublish: usage: ...` (no mention of the flag), no stdout, nothing read or written, value not echoed. Existing exit codes and fixed texts are unchanged; the `invalid_request` sentence no longer says "publisher".

### STOPPED: the commit SHA (part c)
Not built. No `--commit-sha` flag exists. Reason: the Record's payload guard (A184, `record/payloadguard`) refuses any payload string with a run of more than four digits unless it is a typed ID, an RFC 3339 time or a `sha256:` hash. A bare 40-hex git SHA has no exempt shape. A simulation of 200 000 random 40-hex strings (python, this session) found a run of five or more decimal digits in 81.9 percent, so `commit_sha_claim` would make a publication fail about four times in five, and the failure would depend on the SHA. The brief forbids loosening the guard, and the guard is outside the allowlist. The payload itself is free-form in the contracts (no `POLICY_PUBLISHED` payload schema; `grep` of `contracts/` and `tools/`), so no contract is in the way. Options for the Architect, smallest first: (a) leave the SHA out of the Record and print it in the stdout log line only, as a claim; (b) add a typed shape for a claimed git commit to the guard (for example a prefix and 40 hex with a letter in the body, like the other typed shapes), then add an optional `--commit-sha` (40 lower-case hex, absent means the field is omitted, recorded as `commit_sha_claim`, never compared, never a condition); (c) record it as a `sha256:` digest of the SHA string (loses readability). My choice if (b) is ruled: optional, not required, because a required claim cannot be checked and would only teach callers to type anything. Not verified: how the commit SHA is to reach the command in the compose seed step.
