## Session summary
- What changed (PR noema#716): `services/core/migrations/0030_tenant_row_security.sql` (ENABLE and FORCE row-level security on `tenant`; policies `tenant_own_row`, `tenant_verify_read`, `tenant_verify_halt`); `services/core/platform/db/tenant_row_security_test.go`; the 0030 paragraph of `services/core/migrations/README.md`.
- Why: the Security Reviewer's P2 on noema#658 (REQ-SEC-004): every power login could SELECT `tenant` and enumerate every tenant's ID and name. Policy design in the migration's header comment: each power login sees only its own tenant row (`decision_login_tenant()`, as in 0018), the chain verifier lists every tenant and can only leave a tenant stopped, nothing else gets a policy.
- Readers and writers of `tenant` (all enumerated; code reads only `kill_switch` and the tenant list): Execution E6 `Ledger.WritesEnabled` and E8 `Ledger.spend` run as the tenant's `execution_rw__<tenant>` login; Trust T3 (the kill switch read of noema#703) runs as `trust_rw__<tenant>`; the verifier's `tenants()`, `RunTenant` and `halt` run as `noema_verify` (member of `record_verify`); the foreign keys of every table with a `tenant_id`, `tenant_login` included, run as the table's owner; `tenant_kill_switch_guard` reads `pg_roles` only; no SECURITY DEFINER function reads `tenant`; the tenant rows themselves are created outside the repository by the operator (`provision-tenants.sh` says "the tenant-creation step, which must run first"; `test_init.sh` uses the superuser).
- Risks, and how they are contained: (1) FORCE means a non-superuser owner (the migration login) reads and writes no tenant row without a tenant mapping, so tenant creation is the operator's superuser at init (ruling); tests pin the behaviour. (2) Foreign-key checks under FORCE: proven by test with a non-superuser owner (`noema_migrator`): the check still reads the row it needs. (3) The verifier's UPDATE needs a policy once row security is on; its WITH CHECK is `kill_switch`.
- Tests added (REQ-SEC-004; INV-11, INV-12): `TestEachPowerLoginSeesExactlyItsOwnTenantRow` (5 groups x 3 tenants: own row only, no other ID, name, switch; no writes), `TestAPowerRoleWithNoTenantMappingSeesNoTenantRow`, `TestTheRecordReadLoginStillHoldsNoPrivilegeOnTheTenantTable`, `TestOnlyASuperuserCreatesATenant`, `TestTheKillSwitchOfATenantIsReadByItsOwnLoginsOnly`, `TestTheVerifierListsEveryTenantAndSetsTheKillSwitchUnderItsOwnPolicy`, `TestTheVerifiersPolicyAloneRefusesToClearTheKillSwitch`, `TestTenantForcesRowSecurityWithOnePolicyPerRoleGroup` (exact policy set), `TestForcedRowSecurityOnTenantDoesNotBreakForeignKeyChecksOfANonSuperuserOwner`.
