# Session 2026-11-18 12:39 WAT · SEC-08 migration 0030

## Session summary
- What changed (PR noema#716): `services/core/migrations/0030_tenant_row_security.sql` (ENABLE and FORCE row-level security on `tenant`; policies `tenant_own_row`, `tenant_verify_read`, `tenant_verify_halt`); `services/core/platform/db/tenant_row_security_test.go`; the 0030 paragraph of `services/core/migrations/README.md`.
- Why: the Security Reviewer's P2 on noema#658 (REQ-SEC-004): every power login could SELECT `tenant` and enumerate every tenant's ID and name. Policy design in the migration's header comment: each power login sees only its own tenant row (`decision_login_tenant()`, as in 0018), the chain verifier lists every tenant and can only leave a tenant stopped, nothing else gets a policy.
- Readers and writers of `tenant` (all enumerated; code reads only `kill_switch` and the tenant list): Execution E6 `Ledger.WritesEnabled` and E8 `Ledger.spend` run as the tenant's `execution_rw__<tenant>` login; Trust T3 (the kill switch read of noema#703) runs as `trust_rw__<tenant>`; the verifier's `tenants()`, `RunTenant` and `halt` run as `noema_verify` (member of `record_verify`); the foreign keys of every table with a `tenant_id`, `tenant_login` included, run as the table's owner; `tenant_kill_switch_guard` reads `pg_roles` only; no SECURITY DEFINER function reads `tenant`; the tenant rows themselves are created outside the repository by the operator (`provision-tenants.sh` says "the tenant-creation step, which must run first"; `test_init.sh` uses the superuser).
- Risks, and how they are contained: (1) FORCE means a non-superuser owner (the migration login) reads and writes no tenant row without a tenant mapping, so tenant creation is the operator's superuser at init (ruling); tests pin the behaviour. (2) Foreign-key checks under FORCE: proven by test with a non-superuser owner (`noema_migrator`): the check still reads the row it needs. (3) The verifier's UPDATE needs a policy once row security is on; its WITH CHECK is `kill_switch`.
- Tests added (REQ-SEC-004; INV-11, INV-12): `TestEachPowerLoginSeesExactlyItsOwnTenantRow` (5 groups x 3 tenants: own row only, no other ID, name, switch; no writes), `TestAPowerRoleWithNoTenantMappingSeesNoTenantRow`, `TestTheRecordReadLoginStillHoldsNoPrivilegeOnTheTenantTable`, `TestOnlyASuperuserCreatesATenant`, `TestTheKillSwitchOfATenantIsReadByItsOwnLoginsOnly`, `TestTheVerifierListsEveryTenantAndSetsTheKillSwitchUnderItsOwnPolicy`, `TestTheVerifiersPolicyAloneRefusesToClearTheKillSwitch`, `TestTenantForcesRowSecurityWithOnePolicyPerRoleGroup` (exact policy set), `TestForcedRowSecurityOnTenantDoesNotBreakForeignKeyChecksOfANonSuperuserOwner`. Red first at `368e37de`; the existing kill switch, verify, execution, trust and Record suites are unchanged and green.
- Regression cases added: the tests above. Debt entries: closes DEBT-43 when this merges (the Steward moves it; the docs repository is not touched here). Conflicts raised: none.
- Rulings on noema#716 (Architect, relayed by the user, interim), applied in commits `95d6fb40` (red) and the one after it (green): (1) the `GRANT EXECUTE ON FUNCTION decision_login_tenant() TO record_read` and `record_read` in `tenant_own_row` are removed. The `record_read` case of the existing `TestNoRuntimeLoginCanClearTheKillSwitchEvenWithTheGrant` (`platform/db/kill_switch_test.go`) now accepts "no error, zero rows, switch unchanged" instead of the guard's refusal; it is the only expectation changed, the other five groups and every other assertion of that test (the switch is still on afterwards) are untouched, because no policy covers a group that holds no privilege on `tenant`. (2) Tenant creation is an init-time step of the operator's superuser: no policy and no role is made for it; `TestOnlyASuperuserCreatesATenant` documents that the non-superuser migration login cannot insert a tenant under FORCE. (3) The verifier's `tenant_verify_halt` (`WITH CHECK (kill_switch)`) stays.

# Session 2026-11-19 · SEC-08 tenant creation by the operator's superuser (noema#716, ruling A353, relayed, interim)

## Session summary
- What changed: new `deploy/compose/postgres/create-tenants.sh`; `test_init.sh` and `test_provision_env.sh` extended; comments and READMEs point to it (`provision-tenants.sh` header, `deploy/compose/README.md`, `services/core/migrations/README.md`, the 0030 header comment; 0030 is this PR's own, unmerged, no statement changed). Red first at `deb12b11`.
- Why: with FORCE row security on `tenant` and no INSERT policy, only a superuser can create a tenant. Before this change no script in the repository created one: `provision-tenants.sh` said "the tenant-creation step, which must run first" and no such step existed; `test_init.sh` inserted the row by hand as the superuser. Searched outside Go tests (every file type, `_test.go`, `test_*.sh` and `*.md` excluded): the only creator is now `create-tenants.sh`; the bench scripts, `cmd/` tools and `tools/` create none.
- Why not `init.sh`: it runs once at first start of an empty volume (docker-entrypoint-initdb.d), before any migration, so `tenant` does not exist yet; and it is listed protected in this file. The operator's superuser step is therefore a separate script run after the migrations and before `provision-tenants.sh` (which needs the tenant row for its foreign key). Open for the Architect: whether compose should run it as a one-shot service or leave it to the operator's runbook; no compose file was changed (there is no migrate or provision service in compose yet).
- Behaviour: reads `NOEMA_TENANTS` as `provision-tenants.sh` does; validates every ID; refuses unless `current_user` is a superuser; `INSERT ... ON CONFLICT (tenant_id) DO NOTHING` (the key allows it), the name is the tenant ID, the kill switch off by default; an existing row is never rewritten. No password is read, set or passed: the libpq environment only.
- Risks: a superuser connection is needed at deploy time (it is the existing bootstrap credential, trusted on the container socket); an operator who runs it as another role is refused with a message that names no secret.
- Tests (REQ-SEC-004; INV-12): `test_init.sh` proves (a) no power login and not the migration login inserts a tenant, and the script refuses to run as the migration login, creating nothing; (b) run as the superuser it creates `ten_aa` with the kill switch off; (c) a second run leaves name and `created_at` alone and keeps a kill switch an operator set; then `provision-tenants.sh` maps the 7 logins as before. `test_provision_env.sh`: dry run and `.env` handling, an invalid ID refused, the script handles no password, and a static guard that no other non-test file inserts into `tenant`. CI: both run in the existing `compose-scripts` job (path filter `deploy/compose/`), no workflow change.
- Run here: both scripts, as the `postgres` OS user against a throwaway PostgreSQL 16 with pgsodium (`PG_BIN=/usr/lib/postgresql/16/bin`); CI uses 17.11 in the pinned image, which was not run (no Docker daemon).
- Review: `deploy/` paths need the Security Reviewer. Tier 1 path.
