### Doubts and flags
1. **The contract field name `evidence_set_hash` now holds a CONTENT hash in the confirmation binding** (confirmation-request.v1 and the binding of SoT 43.2a say "evidence_set_hash"). Not renamed (no contract change; AGENT-15 would need a version bump). The snapshot's own `evidence_set_hash` (the set hash over IDs) stays in `context_snapshot` and the Decision Record. Architect: say whether the contract should name it (a contract version).
2. **The grant's `evidence_set_hash` and the Writer's `bindingOf`.** The Writer computes an ALLOW's binding from its own step: `s.EvidenceSetHash` of `grants.Step`. For the ALLOW to match the approved binding, the composition's Recorder adapter (EL's, not built) must put the SAME content hash in `grants.Step.EvidenceSetHash` that T9 gave in `FreshBinding` (so the grant then binds the content hash, not the set hash over IDs). `RecordStep` (intake port) carries no evidence hash today. Not done here: out of the allowlist and a design call for the Architect and EL. Without it the ALLOW after an ACCEPT is refused with `ErrConfirmationNotValid`.
3. **Duplicates (A365): defined as one fact, not refused.** The safer-looking alternative (refuse) would make a snapshot that holds one record twice un-confirmable. If the ruling meant refusal, `ContentHash` is one `if` (and its test).
4. **A366 goes beyond "the key includes the state" by one Writer rule:** a tuple has at most one decision of an OUTCOME across states (`otherState`, under the tuple's advisory lock), so a different confirmation, or none, after a stored ALLOW is `ErrDecisionConflict` (the test list of the brief: "a different confirmation id gives a typed conflict"; and A233's retry test, which pins "none"). The DATABASE key alone does not stop two ALLOWs resting on two requests (it is the ruled index); a partial unique index over the tuple `WHERE confirmation_request_id IS NOT NULL` would make that a database rule too. Not added (stricter than ruled); Architect's call.
5. **A declined REJECT's state is the caller's claim.** `Request.DeclinedRequestID` is shape-checked only: the Writer cannot verify a decline (no declined store on main; the confirmation store of noema#756 is not merged here). Trust is the only caller; EL's Recorder adapter must pass the `RequestID` of the declined answer. The field is new in `recorder.Request` (trust/** is in the allowlist) and the intake's `RecordRequest` does not carry it yet: **EL's adapter or a follow-up must map the declined request ID into it.** (The intake README says the Declined answer carries `RequestID`.)
6. **0034 is numbered by me.** 0030 (noema#716), 0031, 0032 (noema#756) and 0033 are registered; only 0031 is on main. Confirm on the ledger of noema#183 before pushing. **The migration needs an independent read** (AGENTS section 11: Tier 1; the unique-index swap and the CHECK are the points). `services/core/migrations/README.md` was NOT edited (A145). `docs/db_schema.md` does not exist in this repository, so nothing generated was updated. The migration fails (and changes nothing) if rows already hold a duplicate of the new key; on a database that satisfied 0027's key it cannot.
7. **Does the content hash make A366 unnecessary for correctness?** No. With the content hash a re-evaluation can seal a new snapshot (new tuple), so the old STOP 2 was avoidable by that route; A366 lets the ALLOW or the REJECT be recorded on the SAME snapshot as the CONFIRM (a re-evaluation that reads the same snapshot, which the A186 replay also does). Both are implemented as ruled.
8. **Not done, noted (not mine):** `Status` of EL's Confirmations adapter (noema#750) must return Pending with a NEW request when the open request's binding no longer describes this evaluation (the Security Reviewer's note); `Status` must also use the content hash and the `sha256:` composite as `FreshBinding` passes them. The end-to-end test of the brief is in two parts: the adapter and `confirm.Resolve` over the real database (above), and the Writer's CONFIRM and ALLOW over the real database (recorder tests); no single test records a CONFIRM through the Writer with a binding over a snapshot read by the adapter, because the Writer tests and the adapter tests live in different packages with different worlds and the Recorder adapter that joins them does not exist yet.
