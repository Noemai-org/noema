# trust

**What it does.** The Trust Engine: reconciliation at decision time, authority, policy, clocks, decisions, grants, confirmations.

**REQs.** REQ-TRU-001, REQ-TRU-002, REQ-TRU-008, REQ-TRU-009, REQ-NFR-002.

**Status.** Empty boundary package (PLT-01). PLT-01 creates the boundary; filled by TRU-01 to TRU-12. The import rules and prohibitions are in `doc.go`.

**Tests.** `go test -race ./trust/...` from `services/core/`.

**Gate order (TRU-02).** `decide.Evaluate` runs the caller's step functions T1 to T15 in the fixed order of PERD §23.3 and returns one decision plus an `evaluation_trace` of step IDs and results (`PASSED`, `TERMINAL`, `FAILED`, `PANICKED`, `DEADLINE`, `INVALID_RESULT`). A step may stop only with the outcomes of its §23.3 row, or UNKNOWN; ALLOW only at T15. A panic, an error, a done context, a missing step, a refused outcome, a decision for another intent version and a T15 that does not decide all end in UNKNOWN `INTERNAL_ERROR` (REQ-TRU-002, INV-16). Evaluate reads nothing itself: the steps carry their ports, so a REJECT at T4 to T6 happens before any read. The steps T7 to T15 themselves arrive with TRU-03 to TRU-11; the Trust intake that builds them is not built yet.

**Proposer swap (decision half).** `decide/proposer_swap_test.go` runs the real `Admit` and `FailAtGate` on two proposers' Intent Objects and keeps `synthetic/proposer_swap/decisions.json` current (`status/ENV-08.md`). Test code only; its `intake` is a stand-in for the unbuilt Trust intake. It validates the decision path only.

**Decision determinism (TRU-09).** `decide.InputHash` is the decision input hash recorded with a decision (REQ-TRU-007, INV-21): `sha256:` of the length-prefixed intent hash, sealed-snapshot hash, pack version, clock reading and distinct policy versions (sorted, so their order never matters), under the domain tag `noema/decision-input/v1`. Golden vectors come from an independent Python implementation. A decision is a pure function of those inputs: 10,000 concurrent replays of the same inputs give identical decisions and traces. The Decision Record that stores the hash is TRU-05.

**Decision basis (TRU-01).** A `decide.Decision` can carry a `Basis`: the pack version, the policy version of each rule that decided (INV-09), the sealed evidence snapshot ID, the freshness of the evidence, and the evaluation time (REQ-TRU-001). `WithBasis` attaches it once; an ALLOW or CONFIRM is refused without the policy rules, snapshot and freshness (`ErrBasisIncomplete`); a refusal before any evidence is read needs only the pack version and the time. The Decision Record that signs and stores it is TRU-05.

**One decision per input and confirmation state (A172, A186, A366; migrations 0027 and 0034).** `recorder.Writer.Write` writes a Decision Record once for its full input tuple (tenant, intent ID, intent hash, sealed context snapshot, policy version) and its confirmation state (the confirmation request the decision rests on: for an ALLOW that follows a confirmation, the request that confirmation resolved; for a REJECT DECLINED_BY_APPROVER, `Request.DeclinedRequestID`; NULL for every other decision); the unique index is `decision_record_input_state_key`, over the tuple and `COALESCE(confirmation_request_id, '')`, so a stored CONFIRM and the ALLOW or REJECT that rests on its request are two decisions of one snapshot. The writer also refuses, under the tuple's advisory lock, a second decision of the same outcome in another state (`ErrDecisionConflict`). Migration 0034 is numbered by C1 and to be confirmed on the ledger of noema#183. Asking again for the same tuple returns the stored record and its grants and writes nothing; a stored decision that the new evaluation contradicts is `ErrDecisionConflict`. A new snapshot or another policy version is a new decision. **A re-evaluation (after a WAIT, a confirmation expiry or a recovery) must seal a new snapshot** (every seal mints its own snapshot ID); a caller that names the old snapshot again gets the stored decision, or `ErrDecisionConflict` if the new outcome differs. The orchestrator's write path owes this and will test it (WAIT then a later decision: `TestAWaitThenALaterDecisionUnderANewSnapshotAreTwoDecisions` pins the writer's side). The writer sets no isolation level (READ COMMITTED); under a stricter level a second writer could meet the unique index as a raw 23505, which also fails closed.

**Disposition linkage (TRU-10; REQ-TRU-010, INV-25; ruling A297, interim).** A decision that names its `DispositionDecisionID` must name an existing ESCALATE decision of its own tenant (`ErrDispositionNotValid`: missing, another tenant's and another outcome are one answer), and every step it carries must be a capability of the pack's escalation plan (`ErrStepOutsideEscalation`). The set is `recorder.Writer.Escalation`, an `EscalationSet` the composition root builds from pack data; the recorder holds no capability ID. Both refuse before anything is written. A decision that names no disposition is unaffected. The adapter that derives the set from the pack's escalation plan is not built. Tests: `trust/recorder/escalation_link_test.go`.

**Provisional limits as pack data (TRU-06).** `platform/trustlimits.Load` reads `trust-limits.v1` (`packs/fintech/limits/trust_limits.json`): the ambiguity absolute floor (PERD v1.23 line 1772) and the clock AT_RISK threshold (line 2134) as integer basis points, with no default (A205 Q1, AGENT-16). Both are NON-CANONICAL until GOV-06. No Trust step reads it yet; it lives in `platform/` (like `platform/masking`) because the `threshold-literal` lint forbids any number but 0 and 1 in `trust/`, and the loader holds the 10000 of the contract's BasisPoints range. A Trust step takes the two integers as inputs; it need not import the package. See `platform/trustlimits/README.md`.

**Tenant kill switch, Trust side (EXE-06, ruling A297 interim; REQ-EXE-008, REQ-OPS-002).** `recorder.Writer.Write` refuses a request that carries steps with `ErrWritesDisabled` (the contract's `WRITES_DISABLED`) while `tenant.kill_switch` is on for the request's tenant, before anything is written: no decision record, no grant, no event (PUS-06: zero `GRANT_ISSUED` events). A request with no step still records. The read is on the caller's transaction as a plain `SELECT` by the Trust login (`SELECT` on `tenant`, migration 0001), so it holds no lock: a switch turned on between that read and the commit is caught by Execution's own read inside the spend (E6, E8), not here. Tests: `trust/recorder/kill_switch_test.go`. Not built: the ops-API listener and the clear path, `KILL_SWITCH_*` events, the Execution-side change (Execution already reads the switch).
