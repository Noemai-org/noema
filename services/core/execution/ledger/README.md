# execution/ledger

**What it does.** The Postgres implementation of the controller's `Ledger` and `GrantSource` ports, plus the kill-switch read for `Binder.WritesEnabled`. Every method is one transaction run as the `execution_rw` role.

**REQs.** REQ-EXE-001 (single use by unique constraint on `grant_id` and `nonce`), REQ-EXE-002 (the key is committed before dispatch), REQ-EXE-006 (the sweeper's input), REQ-EXE-008 (the kill switch is read inside the spend), REQ-AUD-001 (Record events appended in the transaction of the object write; an append failure fails the step, EC-E16).

**How the steps map.**
- `Spend` is E8: SERIALIZABLE; checks the grant is `ISSUED`, reads the kill switch, upserts `idempotency_record` (attempt + 1; the same key with other parameters or another action is a collision, EC-E06), inserts `grant_spend` with the key and attempt, marks the grant `SPENT`, appends `GRANT_SPENT` and `DISPATCH_ATTEMPTED`. A grant that is no longer `ISSUED`, or that loses a race, is a replay. A transaction the database refuses with a serialization failure is run again (see "The retry on a serialization failure" below). A collision raises `SECURITY_EVENT IDEMPOTENCY_COLLISION` and returns `controller.ErrKeyCollision`, which the controller answers by voiding the grant.
- `Void` marks the grant `VOID`, inserts one `recovery_request`, enqueues `recovery.requested` and appends `GRANT_VOIDED`, once per grant.
- `Complete` never sees a receipt whose HMAC did not verify: the Controller verifies it (`Controller.completeReceipt`, `KeyRing.VerifyWith` over the canonical JSON of the signed document) before it calls `Complete`, for the receipt of a dispatch and for the sweeper's; a failed verification returns `ErrReceiptSignature`, writes no receipt and appends one `SECURITY_EVENT` `SIGNATURE_INVALID` through `Ledger.Append`, in a transaction of its own (EXE-04, founder's decisions of 28 and 29 Oct; DEC-2026-10-28 §7). If that append fails, nothing is written and the caller gets both errors.
- `Complete` of a `REJECTED_STALE_VERSION` receipt (REQ-EXE-004, EXE-04; PERD v1.18 §38.2) also voids the spent grant in the same transaction, after `RECEIPT`: the grant moves `SPENT → VOID` (migration `0002` lets the trigger allow it only for a confirmed refusal), one `recovery_request` (reason `REJECTED_STALE_VERSION`), the `recovery.requested` event and `GRANT_VOIDED`, whose payload names `from_status` `SPENT`, `to_status` `VOID` and the receipt. `GRANT_SPENT` stays on the Record. If any of these cannot be written, none is, and the sweeper handles the attempt.
- `Complete` is E11: inserts the signed receipt (first writer wins), moves the idempotency record to `RECEIPTED`, enqueues `outcome.verify` and appends `RECEIPT`, in one transaction.
- `Dispatching` lists spent attempts with no receipt.

**Not here.** The `Binder` reads of the intent, the decision and the plan (Trust and the registry are not built), the `Revalidator`, the dispatcher and the sweeper's age threshold. The sweeper writes receipts for every unreceipted attempt it sees; a threshold so that it does not race a dispatch still in flight is configuration (REQ-OPS-003) and is not built.

**Tests.** `go test ./execution/ledger/...` from `services/core/`, against a real PostgreSQL (`internal/testpg`) with the real controller: a clean run in order, 100 concurrent executes of one grant (one dispatch), void and recovery request, kill switch flipped between E6 and E8, crash after the spend and the sweep, a failed Record append failing the spend, a retry under a new grant, key collision, first-writer-wins receipts, grant loading, deadlines.

## StoreBinder (TRU-08, DEBT-23)

`binder.go`: the production `controller.Binder`. Its database half reads, as the tenant's Execution login, the active policy version (`policy_publication`, highest `version_key`) and whether a grant's decision is still an ALLOW under it (`decision_record`). Fails closed: no publication, no decision, a decision that is not an ALLOW, another version and another tenant's grant all answer "no". The intent hash (E3) and the stored plan (E5) come from `IntentSource` and `PlanSource`, which other tasks build and `cmd/core` plugs in; an unwired source is `ErrBinderNotWired`, never an empty answer. The binder reads only the decision's outcome and compares the grant's own policy version with the active one; it does not compare the grant with the decision's `policy_versions_json`. That equality is guaranteed at issue time by the database trigger from #168 (a grant's policy version must equal its decision record's), and the grant is HMAC-bound, so a grant cannot carry another version afterwards. Tests: `go test ./execution/ledger/ -run 'ActivePolicy|StillAllowed|NeverAllowed|AnotherTenants|NeedsADeadline|PassesTheIntent|RecordedDecisionThatIsNot'` (needs PostgreSQL).

## The dispatch budget (RCV-02 slice 2, ruling A153)

The database refuses the third spend of a key: migration `0023` puts a guard on the insert into `grant_spend` that counts the key's `DISPATCH_ATTEMPTED` events in the Record (the key is the grant's tenant, correlation, capability and target; the ceiling is 2, ruling A3 and A62) and raises `NS002`. `Spend` rolls back as a whole, reports `SpendResult.BudgetSpent` and writes nothing; the controller answers `Outcome.BudgetSpent`, the grant stays ISSUED, and the database refuses it again each time. An earlier dispatch event whose key cannot be read counts against every key of its correlation, and a grant whose key cannot be read is refused. Tests: `budget_test.go`.

## The retry on a serialization failure (noema#714, Architect rulings A317 to A328, relayed, interim)

Spends of one tenant all append to one Record chain head, and PostgreSQL may refuse one SERIALIZABLE spend with SQLSTATE `40001`, at a statement (the idempotency record, the head lock) or at the commit. Such a spend wrote nothing, so `Spend` runs the whole transaction again (`retry.go`, `spendWithRetry`):

- **Attempts.** `Ledger.SerializationAttempts` is the total number of attempts, the first included. It comes from the environment setting `NOEMA_DB_SERIALIZATION_ATTEMPTS` (ruled value 3) and has **no default** (AGENT-16): a `Ledger` with a value below 1 refuses to spend (`ledger: NOEMA_DB_SERIALIZATION_ATTEMPTS is required...`), writing nothing.
- **Where the setting is read.** `Ledger` is not built in `cmd/core` yet; today only tests build it. The composition root that builds it must call `ledger.ParseSerializationAttempts(os.Getenv(ledger.EnvSerializationAttempts))` and refuse to start on its error, which names the setting (missing, empty, zero, negative, signed, padded, non-numeric or out of range). The setting is not yet in `deploy/` (a protected path): see `status/EXE-RETRY-714.md`.
- **Each attempt is a fresh transaction.** Its first statement reads the grant again, so a grant that an earlier winner spent is answered as a replay, and a key whose dispatch budget the winners used up is answered `BudgetSpent`. A failed attempt left nothing behind (idempotency attempt, `grant_spend`, Record events).
- **Only `40001` is retried.** A unique violation, a deadlock (`40P01`) and every other error end the call after one attempt, as before. The context deadline bounds all the attempts: none starts once it is done. There is no pause between attempts.
- **After the last attempt** the error is the one `Spend` always returned: `ledger: spend <grant> did not commit: ...`, unless the grant has meanwhile become final, which is a replay.
- **What the bound does and does not do.** For spends of one dispatch key (budget 2, A3, A62, A153) the Record chain takes at most two commits, so a spend fails with `40001` at most twice, and its third attempt meets a spent budget: three attempts absorb that contention. It is not a proof for many spends of *distinct* keys of one tenant: each round of contention commits one spend, and three attempts do not cover eight such spends. That caller still gets the `40001` "did not commit" error and may present the grant again (the grant is still `ISSUED`); an Architect decision on a larger bound or a caller-side retry is open (see the status file).

Tests (`retry_test.go`, needs PostgreSQL): `go test ./execution/ledger/ -run 'ThreeAttempts|OneAttempt|LosesTheRace|RefusedTwice|LastAttempt|OnlyASerialization|DeadlineStops|WithoutSerializationAttempts|SerializationAttemptsSetting'`. Real contention with one attempt (a held chain head, spends queued behind it: every queued spend is refused with 40001 while its grant is still `ISSUED`); real contention with three attempts (eight grants of one key: two spend, six are over budget, none fails; repeated five times per run); eight callers of one grant (one spends, seven replay); exact attempt counts, non-`40001` codes and the deadline, measured with a trigger on `grant_spend` that counts calls in a sequence and raises a given SQLSTATE (a real race cannot be made to fail an exact number of times, nor to raise a deadlock or a unique violation on demand); the strict reading of the setting.
