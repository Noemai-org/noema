# edge/events

**What it does.** The server-sent events route of the public API (EDG-02, ruling A170): `GET /v1/conversations/{conversation_ref}/events` streams the `progress`, `clarification`, `confirmation`, `answer` and `error` events of one conversation (PERD 39.2). It writes only what a `Feed` returns as committed state (PERD 40). The feed is asked as the verified session's principal and tenant (INV-12); a conversation that is not the caller's is the same 404 as one that does not exist (REQ-API-002). A free-text field goes through the injected masker (A154); a ref is exempt from masking only if it is exactly the contract ID of the type its key names (`refPrefix`: key to `common.v1` prefix, body `[0-9A-Za-z]{2,32}`); a key outside that table, or a value of another shape (for example `acct_0123456789`), is a bad event and nothing of it is written; numbers and instants are typed, so no exemption list is needed here. `Last-Event-ID` resumes after a cursor. A bad event ends the stream with `event: error` / `STREAM_FAULT` and writes nothing of it; a feed failure after the stream began is `STREAM_UNAVAILABLE`. A keepalive comment is sent when a poll returns nothing. Every limit (poll interval, stream limit, event bytes) is configuration.

**REQs.** REQ-API-001, REQ-API-002, REQ-SEC-003. SoT: INV-12, AGENT-13.

**Not here.** The `Feed` over PostgreSQL (it needs the per-tenant reader, OD-P-82: a file-mounted read-only DSN per tenant; the route stays unmounted until configured); the mount line in `cmd/core` `apiRoutes` (after noema#486); the platform redactor as the masker (noema#457; the masker is injected); the clarification and confirmation producers.

**Tests.** `go test ./edge/events/` from `services/core/` (no database).

**Lifetime and limits (reviewer findings on `2229520f`).** A stream never outlives the session's token: its deadline is the smaller of `MaxStream` and the token's remaining life by the injected clock, and a token already at its expiry gets 401 and no stream. Each write has a deadline (`WriteTimeout`, from the injected clock) and a failed write ends the stream, so a slow or gone consumer loses it. Open streams are capped overall (`MaxStreams`) and per tenant and principal (`MaxStreamsPerPrincipal`); a refused stream is the retryable 503 `DEPENDENCY_UNAVAILABLE` (the error catalogue has no generic rate-limit code; a 429 would need an `errors.v3` code, an [OPEN] item for the Steward). A Feed answer larger than `MaxBatch` is a bad answer (`STREAM_FAULT`, nothing of it written). The handler checks that the role is `customer` itself and answers the same 404 otherwise, besides the mount's role gate. The response carries `X-Accel-Buffering: no`.

**What an event may carry (reviewer finding on `e87e38c2`).** `Fields` and `Numbers` carry only what the configured `Vocabulary` lists for the event's kind: a field key or number key that is not listed is a bad event (`STREAM_FAULT`, nothing of the event written); a number must be between 0 and the maximum listed for its key, and every maximum has at most `MaxNumberDigits` digits (the masking limit of A154), so no number can be an account-length run. The vocabulary is configuration with no default (AGENT-16): the contents of an event are the mounting task's decision, and `New` refuses a vocabulary that lacks a kind, names an unknown one, has a key out of form or a maximum over the digit bound. A writer that cannot take a write deadline (`http.ResponseController`) gets 500 `INTERNAL_SAFETY_BLOCK` and no stream: it would be unprotected from a slow consumer.

**Not here, stated.** (1) Only a fake Feed exists: isolation and the end-to-end path are proved against the port, not against the per-tenant reader (OD-P-82) and the platform masker (noema#457); the masker is injected, so any separator gap in it applies to whatever is wired. (2) A session that is closed or revoked mid-stream is not noticed; only its expiry ends the stream (the token's remaining life). (3) `MaxBatch` bounds what is written, not what the Feed builds in memory: the Feed's own limit belongs to the Feed. (4) The session Verifier refuses an empty subject and a tenant that is not served, so the stream-cap key (tenant and principal) is never empty.
