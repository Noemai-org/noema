# Intron baseline run: plan (DRAFT, Voice Engineer, 19 Nov 2026)

Status: DRAFT for the Founder and the Architect to read before the key arrives. It decides nothing and sets no threshold (AGENT-16). Task VOI-16; REQ-VOI-001, REQ-NFR-003; rulings A180, A241, A324. Every vendor limit named here is in `docs/voice/intron-docs-notes-DRAFT.md` (noema#625) with its source page; none is repeated as a number in this plan.

## 1. What the run is, and is not

- It measures, on Intron's **current** streaming endpoints, the time of each stage of one voice turn on short utterances: speech-to-text (end of speech to final transcript), the core (admission and answer text), and text-to-speech (answer text to the first audio chunk). The sum is the number VOI-16 is about.
- It is a **baseline**, not the verdict. By A324 the VOI-16 verdict is taken on Intron's real-time endpoints when they are enabled; a baseline on the current ones is recorded as measured and compared to nothing.
- **Synthetic audio only** (A180): no real speaker audio goes to any vendor until the written terms and the DPA are signed. The utterances are generated by Intron text-to-speech from scripts we write; no script contains a real person's name, number or account.
- The free-minutes split is the Founder's (A324): 20 of the 60 minutes for the baseline, 40 kept for the real-time endpoints.

## 3. The manifest (what is sent)

- **Utterances:** a fixed list of scripts, each one a few sentences of a banking-style request (a transfer, a balance, a dispute), written by Voice, 5 to 15 seconds when spoken (the Founder's measurement condition, passed to the harness as data). Locales: Nigerian English and Nigerian Pidgin, plus English mixed with Yoruba, Igbo and Hausa. Digits appear only as short key values (an amount, the last four digits of a reference).
- **How audio is made:** each script goes through Intron text-to-speech once, 16 kHz PCM16 mono (the only speech-to-text input format, A191), and the result is stored as a synthetic fixture labelled SYNTHETIC (AGENT-25). This costs text-to-speech minutes and is counted in the budget before the call.
- **What is not decided and is asked of Intron (technical session):** which voices exist for Nigerian English and Pidgin, whether streaming speech-to-text returns any per-token confidence, and whether model versions can be pinned. Until answered, the run records `model_version` as "not reported" and every token as low confidence (A173, A228).
- **Accent caveat:** audio made by one text-to-speech voice is not Nigerian speech in the field. The baseline says so in its report; it measures latency, not accuracy.

## 4. The budget, before any call

The harness refuses a session whose audio does not fit the budget the caller sets (`AudioBudget`). Before the first call the runner prints, from the manifest, the audio it will send in each direction: the minutes of synthetic audio generated (text-to-speech), the minutes sent to speech-to-text, and the minutes of answers spoken (text-to-speech again). The Founder reads the three numbers and the total against the 20 minutes. A run that would exceed the total does not start; it is trimmed by removing utterances from the end of the manifest, never by shortening them.

## 5. Pacing and limits

Intron publishes a limit on concurrent sessions and on new connections per minute (the notes file, with its source). The runner paces sessions one after another, with the pause between sessions passed as an argument, so that neither limit is reached; it never retries a refused connection with a new one inside the same session. A quota refusal (`RATE_LIMITED`) ends the session as an incomplete one and ends the run.

## 6. What the run does, step by step

1. Read the key from the file at call time (never from the environment, never logged).
2. Generate the synthetic audio once (section 3), store it, and stop if any generation fails.
3. For each manifest line, in order: one `measure_session` call: speech-to-text on the stored audio, the response stage, text-to-speech to the first chunk. The response stage during the baseline is a fixed stand-in that returns a masked sentence of the same shape as a real answer (the real core is not part of a vendor baseline; its own latency is measured separately and added in the report as a separate row).
4. A session that fails at any stage is kept as an incomplete session with its failure kind. It counts as the worst case in the 95th percentile and is never dropped (`latency.py`).
5. After the last line, or at the first `RATE_LIMITED`, write the report.

## 7. The report (what is written, and what is not)

- Per stage and for the total: the number of sessions, complete and incomplete, the median and the 95th percentile of the complete ones, and the 95th percentile counting each incomplete one as the worst case. The target for VOI-16 is printed beside the total as a fact of the plan (SoT) and no verdict word is written next to the baseline.
- The failures by kind, with counts. No transcript text, no audio and no key appears in the report or the log; a session is named by its manifest label.
- The budget spent, in minutes, in each direction, against the 20.
- The caveats of section 3 and the endpoint version in use as Intron reports it, or "not reported".

## 8. Stop conditions

Stop the run, write down what happened, and ask when: the key file is refused by the reader; any audio would leave the manifest (a file that is not marked synthetic); the budget would be exceeded; a refused connection or quota message appears twice in a row; Intron's response contains anything the adapter does not understand twice in a row (the wire format of a vendor message is one file, `intron_tts_wire.py` or `intron_wire.py`; the first live call may show that a field is spelled differently from the documentation, which is a one-file change in the wire module and its test).
