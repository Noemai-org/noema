# Decision tables: the paths checked for a row-security bypass

**6 Nov 2026 (Engineering Lead), for the Security Reviewer.** As-built, not authority: rulings A6 and A13 of 6 Nov 2026 (Proposed until their record is committed), `services/core/migrations/0012_decision_record.sql`, and the tests named below decide. SYNTHETIC data only. This is the list of what I looked at, so that SR can test what is **not** on it. The first three sections are enforced by tests that read the catalog; the rest is by reading.

## What the migration does (0012)

`decision_record` and `decision_grant`: row-level security **enabled and FORCED**; reads limited to the login's tenant for `trust_rw`, `execution_rw`, `outcome_rw`; Trust inserts and Execution status updates limited to the login's tenant; a trigger on `decision_record` also checks `tenant_login` for the Trust power. The tenant comes from `session_user` through `tenant_login` (`decision_login_tenant()`), never from a value the caller passes.

## Enforced by a test that reads the catalog (`platform/db/rls_paths_test.go`)

1. **Every catalog object that mentions either table is on a reviewed list** (functions by source and by trigger, views and materialised views, rewrite rules, publications). A new one fails `TestEveryPathThatTouchesTheDecisionTablesHasBeenReviewed` until a person reads it. Today: `decision_grant_requires_allow` (invoker, so row security applies to its read of `decision_record`; `search_path = pg_catalog, pg_temp` and `public.decision_record`, because an unpinned invoker trigger would read a temporary `decision_record` first: SR's finding on noema#168, `TestATemporaryTableCannotStandInForTheDecisionRecordInTheGrantGuard`), `decision_grant_guard`, `decision_record_tenant_guard` (definer, `search_path = pg_catalog, pg_temp`, reads `tenant_login` and `pg_roles` only), `reject_mutation`, and `outcome_record_verdict`. No view, rule or publication mentions them.
2. **Every SECURITY DEFINER function that reads either table pins `pg_temp` last** (`TestEveryDefinerThatReadsTheDecisionTablesPinsItsSearchPathWithTempLast`). **This found a real gap:** `outcome_record_verdict` (migration 0007) reads `decision_grant` as a definer with `search_path = pg_catalog, public`. Without `pg_temp` named, PostgreSQL searches the session's temporary schema first for tables, so a login with the TEMPORARY privilege could create `pg_temp.decision_grant` and make the function read forged rows in place of the real table. Migration 0012 (this file's migration; it was numbered 0011 earlier) sets `search_path = pg_catalog, public, pg_temp` on it (setting only, body unchanged). SR: please try to exploit it on the migration 0007 state and confirm 0011 closes it.
3. **Who holds a privilege on either table** (`TestOnlyTheReviewedRolesHoldAPrivilegeOnTheDecisionTables`): `trust_rw` insert and select; `execution_rw` select and update (status only, by column grant and by the guard trigger); `outcome_rw` select. No other non-superuser role holds any.
4. **Definer functions without `pg_temp` pinned that do not read these tables** are listed and the list can only shrink (`TestTheListOfDefinersWithoutPgTempPinnedOnlyShrinks`): `outcome_verdict_complete`, `recovery_request_verdict_guard` (Outcome, migration 0007), and `provision_tenant_login`, `record_insert_t`, `record_lock_head_t`, `record_login_tenant`, `record_read_chain_t` (Record, migrations 0004 and 0006). **They are not fixed here.** The Record ones are Core Engineer 1's under ruling A6; the two Outcome ones are the Outcome owner's. They read other tables, so the same temp-table shadowing applies to those tables. SR: test them first.

## Checked by reading

- **Owner access.** The owner of a table is not subject to row security unless forced; both tables are forced. A superuser bypasses row security whatever is set, and a `BYPASSRLS` role would; no runtime login is either. SR: confirm for the deployed roles (`init.sh`) that no login has `rolsuper` or `rolbypassrls`.
- **`session_user` against `current_user`.** The policies key on `session_user`, so `SET ROLE` does not change the tenant. A superuser who runs `SET ROLE trust_rw` is still a superuser and bypasses. The tests that previously used `SET ROLE` from the administrator now use real tenant logins.
- **Foreign keys.** PostgreSQL checks referential integrity without row security. The keys that point at `decision_grant` (`grant_spend`, receipts, recovery) are by `grant_id`; a login cannot insert a row that points at another tenant's grant because it cannot see the grant to name it, but it could guess an ID: the composite keys that carry `tenant_id` are the defence where they exist. SR: test `grant_spend` and `execution_receipt` for a cross-tenant reference.
- **Disposition link.** `decision_record` references itself by `(tenant_id, disposition_decision_id, disposition_outcome)`, so a link names an ESCALATE decision of the same tenant (a test).
- **Existence oracle (residual).** The primary keys are global (`decision_id`, `grant_id`), so an insert that collides with another tenant's ID fails with a unique violation, which tells the caller the ID exists. IDs are minted by the server (`<prefix>_<ULID>`), not chosen by the caller, so I rate it low; I did not test it.
- **Triggers.** `decision_record_immutable` and `decision_grant_guard` refuse UPDATE and DELETE, `*_no_truncate` refuses TRUNCATE, for every role including the owner. TRUNCATE ignores row security, which is why it is refused by trigger and not by policy.
- **`pg_temp` in the new functions.** `decision_login_tenant` and `decision_record_tenant_guard` are `SECURITY DEFINER`, `SET search_path = pg_catalog, pg_temp`, and schema-qualify `public.tenant_login`.
- **Signing.** Not a database path: see the contract `contracts/schemas/decision-record.v2.json` and rulings A5 and A13 in `docs/decisions/DEC-2026-11-06-architect-rulings.md` (in the `docs` repository); the signing code is `SignRecord` and `VerifyRecord` in `trust/grants/record.go`, which lands with noema#197.

## Not checked (SR, please)

`BYPASSRLS` and superuser membership of the deployed logins; `COPY` and `pg_dump` by a non-owner; logical replication slots; the `LEAKPROOF` question for the policy function (it is a definer with `STABLE`, not marked leakproof, so the planner will not push a user's predicate below it); error-message and timing differences between "no such row" and "not your row"; the Record functions and the two Outcome functions in section 4; extensions. DEBT-06 closes only when SR's row-security tests pass on `main` (ruling A6).

## Addendum, 6 Nov 2026 (Codex P1 on noema#168)

`outcome_record_verdict` is a SECURITY DEFINER function owned by the role that applies the migrations. Under FORCE that owner is subject to the policies, so
`decision_record_read_definer` and `decision_grant_read_definer` (`FOR SELECT TO CURRENT_USER`) let it read the tables it joins. Both still use
`decision_login_tenant()`, which reads `session_user`: the owner sees a tenant's rows only inside a call made by that tenant's login. A superuser owner
bypasses row security, so `TestTheOwnerOfTheVerdictFunctionCanReadTheDecisionTablesItJoins` checks the catalog.

- **Grant insert policy (SR on noema#168, finding 4).** `decision_grant_write` admits `status = 'ISSUED'` only (`TestTrustCannotInsertAGrantThatIsAlreadySpentOrVoid`): Trust cannot create a grant that is already spent, void or expired; only `execution_rw` moves the status (D8).

- **A grant matches its record (ruling of 8 Nov 2026 on noema#329; SR notes 2 and 3 on noema#168).** `decision_record_bound_fields` refuses a record without `intent_id`, `correlation_id`, `policy_version`, `intent_hash`, `issued_at` and `expires_at`, or one that expires when or before it is issued. `decision_grant_requires_allow` refuses a grant whose `intent_hash` or `policy_version` differs from its record's, or that expires after it (document or column). Tests, each seen failing first: `TestADecisionRecordMustCarryItsBoundFieldsAndAWindow`, `TestAGrantCannotOutliveItsDecisionRecord`, `TestAGrantMustCarryTheIntentHashOfItsDecisionRecord`, `TestAGrantMustCarryThePolicyVersionOfItsDecisionRecord`. A date such as 30 February matches the timestamp pattern and fails the cast (class 22, not 23); it is still refused.
