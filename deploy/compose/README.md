# deploy/compose

The POC topology (PLT-04; PERD §65.1, REQ-OPS-001). Local use only.

| Command | What it does |
|---|---|
| `make up` | creates local secret files if missing, then builds and starts Postgres, Temporal, core, model and the UI, waiting for every health check |
| `make net-matrix` | runs the connection-test matrix against the running stack |
| `make bench-smoke` | zero-case deterministic smoke; refuses to run if `benchmark-heldout` is referenced |
| `make model-bench-up` | the bench profile with `bench-model.yml` added: the model service is started through `model_cost.model_app:app` from `benchmark/model_cost` (mounted read-only; the service's own code reads no benchmark variable, ruling A55), with `BENCH_OUT=/bench-out`, a bind mount of the Makefile's `BENCH_OUT` and the invoking user's uid, and each call's cost record is written to `$BENCH_OUT/cost/` (REQ-NFR-007). Only this target adds the file; `make up` and CI never do. Checked with `docker compose config` only (no Docker daemon where it was written) |
| `make bench-up` / `make bench-down` | the full bench stack for a G1 run: the bench profile with `bench-model.yml` (the model's cost files) and `bench-stack.yml` (the core's stand-in settings, the hostility proxy on the stand-in route table, the runner's output directory). The runner is the `bench-runner` container (`services/bench-runner.yml`) on `bench_net` and `edge_net`; run the suite in it with `docker compose ... exec bench-runner python -m benchmark.runner ...` (the dispatch workflow `bench-g1-stack` does, and captures mock-case's live log). `profiles.py` resolves the bench profile with both overlays |
| `make down` | stops the stack, keeps the data volume |
| `make reset` | destroys containers, networks and the data volume of project `noema-local`; refuses any other project name; prints what it will destroy |

## Networks

`edge_net` (ui, core, model; PERD §65.1), `svc_net` (core, model), `data_net` (core, postgres, temporal), `tushe_net` (core), `provider_egress` (model only), `bench_net` (the oracle side: mock-case, its database, the hostility proxy, the stand-in, their anchors, and the bench runner; unreachable from core and model). All of these except `provider_egress` are Docker-internal. One further network, `ui_publish_net`, has the UI as its only member: it is how the UI publishes its port to localhost, and it is the UI's only route out. It is not one of the six networks of PERD §65.1; it exists so that `edge_net` can be internal (see "Routes out").

Profiles: `dev`, `ci`, `bench`, `demo` all start the same five services for now. The bench runner is in `bench` only and sits on `bench_net` and `edge_net`: it is the one caller that reaches both the oracle side and the core's public API, and `netcheck/profiles.py` keeps the core and the model off `bench_net`. The hostility proxy and runner (bench; ENV-09) and the reference partner listener (demo) join later. `netcheck` holds the matrix fixtures and is never started by `make up`.

## Database and secrets

Postgres creates `noema` (owner `noema_migrator`, a `NOLOGIN` role whose only login is `noema_migration_login`; W1 D14a). The core's login `noema_core` is not a superuser, cannot create roles or databases, owns nothing and has no `CREATE` on the database or on `public`; it is never a member of `noema_migrator`. The migration login's password (`noema_migrator_password`) is mounted into `postgres` (the bootstrap) and nowhere else; the one-shot migrate step (EXE-08) will be the second holder. `postgres/assert_roles.sql` pins all of this, run by `make net-matrix` against the stack and by `postgres/test_init.sh` against a throwaway local cluster. Separately, it creates `temporal` and `temporal_visibility` (owner `temporal`, its own password). Noema code never uses the Temporal role. Passwords are random files in `deploy/compose/secrets/` (git-ignored), mounted at `/run/secrets/`. The model service receives no secret and no DB or Temporal variable. The webhook relay is not part of Compose (PERD §65.1).

## The matrix (`netcheck/matrix.py`)

1. The Compose configuration gives each service exactly the networks of PERD §65.1 (written out in the script, independent of the Compose file).
2. A probe that carries each service's networks tries every target. A target must be reachable exactly when a network is shared.
3. The forbidden paths are repeated from inside the real model container.
4. Database roles: `init.sh` creates every role (a migration never does): the group roles `trust_rw`, `execution_rw`, `outcome_rw`, `evidence_rw`, `orchestrator_rw`, `record_append`, `record_read` and `record_verify` (NOLOGIN), the verifier's login `noema_verify`, the evidence recompute's read-only login `evidence_verify` (a member of no role; migration 0020 grants it SELECT on `context_snapshot` and `evidence_item`), and, for each tenant in `NOEMA_TENANTS` (for example `NOEMA_TENANTS="ten_aa ten_bb"`), one login per power named `<group>__<tenant>`. After the migrations, `postgres/create-tenants.sh` (run as the operator's superuser; `tenant` forces row-level security with no INSERT policy, migration 0030, so no other role can create a tenant, and the script refuses to run as one) creates the `tenant` rows for `NOEMA_TENANTS`, and then `postgres/provision-tenants.sh` (run as the migration login, never `noema_core`) adds the `tenant_login` mapping rows; both are idempotent. **Where the step runs (A353):** nothing in Compose applies the migrations or calls `provision-tenants.sh` today (the one-shot `migrate` service is EXE-08, not built), so the operator runs the three steps by hand, in this order, after `make up`: the migrations, then `create-tenants.sh` as the superuser, then `provision-tenants.sh` as the migration login. `init.sh` is unchanged: it runs once on an empty volume, before any migration, when `tenant` does not exist, so it cannot create a tenant. `postgres/test_init.sh` (CI job `compose-scripts`) proves that no power login and not the migration login can create a tenant, that the superuser does, that the script refuses any other role, and that `provision-tenants.sh` run first stops and maps nothing. What is not built: a Compose one-shot service (or the EXE-08 migrate step) that sequences the three steps, so that a stack with no tenant creation fails a check; it is a new service and waits for approval (AGENT-14). The passwords are file-mounted secrets (`noema_verify_password`, `evidence_verify_password`, `noema_tenant_login_password`; one shared tenant-login password in the POC for the power logins, DEBT-13; **each emitter login has its own secret file `secrets/emitter_logins/<tenant>__<emitter>`** (ruling A4), which `init.sh` refuses to start without and refuses if it equals any other secret, and which the shared password never opens, because the core process holds every login and the boundary is the database's mapping). Also: `noema_core` is a plain role; neither the core's role nor Temporal's role can connect to the other's databases.
5. Egress: the core and the model without `provider_egress` cannot reach an outside address; the UI still serves on its published port.

## Routes out

The only networks that are not Docker-internal are `provider_egress` (the model, for providers, PERD §65.1) and `ui_publish_net` (the UI, to publish its port). So:

- the **core** has no route out at all;
- the **model** reaches outside only through `provider_egress`;
- the **UI** reaches outside only through `ui_publish_net`;
- only the UI publishes a port, on `127.0.0.1:8082`.

Step 5 of the matrix proves it: a listener on the host stands for an address outside the stack. The core, and a probe carrying the model's networks minus `provider_egress`, must not reach it; the model (through `provider_egress`) and the UI may. Shared environments still need the host firewall rules REQ-OPS-001 also requires.

## Egress allowlist for the model service's providers

`provider_egress` is the one network that reaches outside (above). Docker cannot name a host, so the allowlist of providers is the **host firewall of the shared environment** (REQ-OPS-001), written from the deployment's settings; **no hostname and no key is in this repository** (a test, `tools/ci/test_check_secret_refs.py`, fails if a file names an Intron endpoint).

| Provider | Allowed from | To | Where the host comes from | Where the key comes from |
|---|---|---|---|---|
| Intron Sahara v2.5 (speech-to-text and text-to-speech; A179) | the model service only (its `provider_egress` address), nothing else | HTTPS, TCP 443, the one host of `INTRON_API_BASE_URL` | the deployment's settings (the name is in `.env.example`; the value is given by the Founder and written only into the firewall rule and the Environment) | a 0600 file the deployment mounts into the model service, named by `INTRON_API_KEY_FILE` (A249); only the model service reads it (INV-29); there is no environment variable for the key, and `netcheck/profiles.py` fails any profile where another service has that setting or a mount named for it, or where any service carries the key as a variable |

The entry opens nothing until the Founder gives the host and the key. Until Intron's data terms are in writing (A180), only synthetic audio goes to it. The same rule applies to any later provider: a named setting for its host, a key file named by a `*_FILE` setting, one row here.

## mTLS between the core and the model service (noema#555)

The model service's listener requires a client certificate signed by the stack's local CA (uvicorn's own `--ssl-*` options, set as `UVICORN_SSL_*` in `services/model/Dockerfile`, `CERT_REQUIRED`); there is no plain HTTP port. `secrets_local.sh` calls `tls_local.sh`, which makes a throwaway CA and three certificates into the git-ignored `secrets/tls/` (OD-P-22) and deletes the CA key: `model.crt/.key` (the model's server certificate), `core-client.crt/.key` (the core's identity) and `model-health.crt/.key` (the model's own health-check client). Each service mounts only its own key and the CA certificate; `netcheck/profiles.py` fails if the core mounts the model's key or the model the core's. The model's health check presents `model-health` on the same listener. The core is given the setting names `NOEMA_MODEL_URL` (`https://model:8081`), `NOEMA_MODEL_TLS_CA_FILE`, `NOEMA_MODEL_TLS_CERT_FILE`, `NOEMA_MODEL_TLS_KEY_FILE`; its client is the Engineering Lead's. SYNTHETIC local material; real certificates are the OQ-09 decision. The compile route stays unwired in `main.py` until this is merged.

## Session tokens in the G1 stack (after noema#444)

`make bench-up` needs `BENCH_MAX_BODY_BYTES` (no default: no body limit is approved in the repository, so a person gives it; the G1 workflow takes it as a required input) and runs `make bench-tokens` first: it builds the Edge's synthetic issuer, makes a throw-away SYNTHETIC ES256 key pair under `$BENCH_OUT/idp` (a 0700 directory, the private key 0600) and writes nothing that is uploaded. The core gets the six `NOEMA_SESSION_*`/`NOEMA_MAX_BODY_BYTES` settings and mounts the **public** key and the pack's session limits only; the runner reads the issuer and the private key from `/bench-out/idp` and issues each principal's token on demand (`--idp-*`). `netcheck/profiles.py` fails if any other service mounts anything of that directory or the core mounts more than the public key.


## The Intron key file (optional bench overlay; A377 to A379)

`bench-intron.yml` mounts the Intron key into the model service so it can go live the day Intron sends it. `make bench-up` adds it only when `NOEMA_BENCH_INTRON_KEY_FILE` names the host file; otherwise the model has no mount, `INTRON_API_KEY_FILE` is unset, the provider is not registered and voice degrades to text (A179). Never a placeholder file. The file is written at run time from the bench Environment (nothing in the repository holds a value), is a regular file (not a link), mode 0600 or 0400, owned by the user the bench model runs as (`bench-model.yml` runs it as the invoking user, `NOEMA_BENCH_UID`; uid 10001 is the image's own user and applies only without that overlay), one printable token of at most 512 bytes; the model's reader refuses anything else at call time. It is mounted read-only at `/run/intron/key` into the model and nothing else (netcheck: the variable and the mount come together, bench profile only, one bind of one file; no other service names or mounts it). Raw audio never passes through it: it lives only in the bench Environment's private store (REQ-VOI-004).

## The bench stack's per-tenant Trust logins (A356, A445; noema#790)

`bench-stack.yml` gives the bench core the Architect's settings (the timeouts, the pack manifest and its bounds, the three paths) and the Trust logins it needs, without ever handing the core a password as a secret of its own:

- **`bench_tenants.sh`** gives the ONE tenant list that `make bench-up` passes to `secrets_local.sh` and to Compose: `NOEMA_TENANTS` in the shell, else in Compose's `.env`, else the stand-in tenant (`BENCH_TENANT`, default `ten_alpha`). Every word must be `ten_` and 2 to 32 letters or digits and the stand-in tenant must be one of them, or it prints nothing and exits non-zero (the list is pasted into a recipe as text, so a quote or `$(...)` in a `.env` value must stop here); `bench-up` stops on an empty list before anything runs.
- **`trust-dsn-init`** is a one-shot (root, no network, read-only root, `cap_drop: [ALL]` plus `CHOWN`, `FOWNER`, `SETUID`, `SETGID`; the secret `noema_tenant_login_password` only). It writes one DSN file per tenant of the list into the `trust_dsns` volume (mode 0400, owner 65532: `trust_rw__<tenant>` login), checks each by reading it as that user, removes the file of a tenant that left the list, and stops on any entry that is not a tenant file. The core mounts the volume read-only at `NOEMA_TRUST_DSN_DIR` and waits for the step. Without `CAP_DAC_OVERRIDE` the step reads the tenant password only because `secrets_local.sh` makes that secret mode 644; a secret at mode 600 (the core-trust seed) will need a different mount for its own one-shot.
- netcheck checks the core's values by number and who holds the password or mounts the volume (`netcheck/profiles.py`).

## The core's other DSN directories, keys and settings (A506, interim; the bench stack)

`bench-stack.yml` gives the bench core every setting the final composition reads (the values are the Architect's, from the code at the heads of noema#838, main and noema#847; each is checked by value in `netcheck/profiles.py`):

- **Four DSN directories**, one file per tenant named exactly the tenant id, written by `trust-dsn-init` (one job per directory, mode 0400, owner 65532, read back as that user): `NOEMA_TRUST_DSN_DIR` (`trust_rw__<t>`), `NOEMA_ORCHESTRATOR_DSN_DIR` (`orchestrator_rw__<t>`), `NOEMA_RECORD_READ_DSN_DIR` (`record_read__<t>`) and `NOEMA_EDGE_DSN_DIR` (`record_emitter__<t>__core-edge`, whose password is that login's own secret in `emitter_logins/`, not the shared tenant password). The first three use the shared tenant login password.
- **Keys**, written by the one-shot `core-keys-init` (no network, `cap_drop: [ALL]` plus `CHOWN`, `DAC_READ_SEARCH` (it must READ secrets that keep the host user's ownership and mode 0600, and writes none), `FOWNER`, `SETUID`, `SETGID`; never `DAC_OVERRIDE`; the three key secrets only; every value checked before anything is written, all different, a directory that holds anything else is refused): `core-workflows.ed25519.1.key` in `NOEMA_ORCHESTRATOR_KEY_DIR`, `core-edge.ed25519.1.key` in `NOEMA_EDGE_KEY_DIR` (one directory per identity, the loader reads every key file of its directory) and the input hash key file `NOEMA_INPUT_HASH_KEY_FILE`; each is 64 lower-case hex characters, mode 0400, owner 65532; `secrets_local.sh` makes the three values (umask 077, kept on a second run). `NOEMA_ORCHESTRATOR_KEY_MAX_ACTIVE` and `NOEMA_EDGE_KEY_MAX_ACTIVE` are 2.
- **The operator one-shots** (bench only; A445, A484, A489, A527). `operator-dsn-init` (no network, `cap_drop: [ALL]` plus `CHOWN`, `FOWNER`, `SETUID`, `SETGID`; the secret `postgres_superuser_password` only) writes the one DSN file `dsn` into the `operator_dsn` volume (mode 0400, owner 65532). `core-trust-keys-init` (the `core-keys-init` script and capabilities; the secret `core_trust_ed25519_seed_1` only) writes `core-trust.ed25519.1.key` into `core_trust_keys` (64 lower-case hex characters, mode 0400, owner 65532). `tenant-init` then runs `tenantinit` from the core image on `data_net` as 65532, with exactly `--dsn-file /run/operator-dsn/dsn --key-dir /run/core-trust-keys --key-max-active 1` and no `--tenant` (tenant rows have one creator, `create-tenants.sh`); it registers the core-trust PUBLIC key with `key_register`, which only the owner and the superuser may call, so its login is the superuser's, and the migration login's password stays with the migrate one-shot and postgres alone (A527). `policy-publish` runs `policypublish` from the same image with the tenant's Trust login file (`trust_dsns`, read-only) and the same key directory (read-only), after `tenant-init`, and the core waits for it. netcheck pins who holds `postgres_superuser_password` (postgres and `operator-dsn-init`) and the core-trust seed (`core-trust-keys-init`), who may mount the two new volumes (the core mounts neither), and every flag of the two commands.
- **Temporal:** namespace `default`, task queue `noema-investigations`, `NOEMA_TEMPORAL_TLS_CA_FILE=/run/tls/ca.crt`; the client certificate and key stay unset (server-side TLS only, DEBT-46). **`NOEMA_TRUST_ESCALATION_GRAPH=fin.graph.escalate`.** The Recorder's lifetimes are EL's values in noema#847's body (grant 600000 ms, record 600000 ms, transaction 10000 ms; the Founder confirms); the grant lifetime must not exceed the record lifetime.
- **Never in Compose:** `NOEMA_WRITE_SWAP_DECISIONS` (a test-only switch). Netcheck fails any service that sets it, or the Temporal client certificate or key.
