# Anchor-store spike (SEC-14)

Date: 2026-11-03. Owner: SR. **Test infrastructure only. Nothing here is adopted.** It tests checks A1 to A7 of `docs/security/sec-14-anchor-store-evaluation.md` (docs repository) against a candidate write-once store for chain-head anchors (REQ-AUD-007). Nothing under `services/` or `contracts/` uses it. A store in a container tests the mechanism and the write-only credential; it does not make the store "separately controlled" (the Architect's principle, 2 Nov 2026: the production store sits in an account whose credentials the runtime operator does not hold).

## Run

`deploy/spike/anchor-store/run.sh seaweedfs` or `run.sh silo` (needs docker and python3). CI: workflow `anchor-store-spike`, which runs only on a pull request that changes these paths, or by hand.

## What it builds

- `seaweedfs/Dockerfile`, `silo/Dockerfile`: the images, pinned by digest (trust-on-first-use from Docker Hub on 2 Nov 2026; no image signature was verified).
- `s3.py`: a standard-library AWS SigV4 client. It checks itself against the signature in AWS's published example before it signs anything, so the spike adds no client dependency.
- `run_a.py`: the checks. A refusal counts only as a 4xx that is a decision of the store; a request the store could not parse is inconclusive and fails. Each refusal names its layer (authorization, object-lock rule, or bucket state, which is not the credential). Rows marked INFO and LIMIT are evidence, not pass or fail.
- `run.sh`: starts the store with only the S3 port published to localhost, creates a write-only writer and a read-only verifier, and runs the checks.

## Credentials

Random per run, generated by `run.sh`, passed by environment, never committed and never printed. (An earlier branch carried fixed synthetic keys; the repository's secret scanner rightly flagged one, so the keys were removed rather than the scanner's rules changed.)

## Limits

Single node only. Upgrades, performance, backups, image signatures and multi-node behaviour are not tested. An operator with access to the store's host or network deletes locked data beneath the S3 API in both stores; the LIMIT rows show it.
